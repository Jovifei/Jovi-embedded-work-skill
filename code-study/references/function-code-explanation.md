# 函数文章规范：第1节看完整原函数，第5节做代码解释

## 1. 固定阅读顺序

每篇函数文章先使用 `## 1. 完整函数体与原注释`，让读者先看到证据原貌；然后进入职责、参数和调用关系；第5节使用 `## 5. 代码解释` 做注释式深入讲解。

### 1.1 第1节的忠实性要求

- 有函数实现时，展示直接绑定该函数的原函数头/文档注释＋完整函数体。
- 第1节不加学习注释，不删原注释，不省略分支，不重排源码。
- 源码位置和行号放在代码块上方，代码块本身保持可复制、可对照。
- 函数体不可见时只展示真实声明并说明边界，不伪造实现。
- 原注释与活动代码矛盾时原样保留，后文指出冲突。

### 1.2 第5节的目标

第5节回答“这些真实语句怎样一起完成本函数职责，为什么按此顺序连接”，不是重新排版源码或输出语法树。短函数可完整展示；长函数按连续职责块展开。行号作为证据，不作为正文主角。

必须先读取函数正文、涉及类型/宏、关键被调用者和适用配置。不能从`Enable/Ready/Lock/Commit`等名字直接推导全部行为；实现未提供时把接口作用与内部未知分开。

## 2. 一块合格解释包含什么

| 层次 | 说明重点 |
|---|---|
| 目的 | 此块在整个函数中解决什么具体问题 |
| 机制 | 输入/状态如何被读取、判断、改变；结果存到哪里或返回给谁 |
| 顺序 | 此块依赖前一步什么结果，为后一步提供什么前提 |
| 理由 | 为什么等待、复核、限幅、先A再B；标明证据等级 |
| 边界 | 条件不成立、循环不退出、参数无效、并发变化、再次调用时怎样 |

简单getter只需解释读取对象、返回值、消费者和并发前提，不强行写复杂硬件推论。

## 3. 推荐版式

````markdown
## 1. 完整函数体与原注释

```c
/* 原函数头注释 */
static void example(void)
{
    real_code();
}
```

## 5. 代码解释

本函数先……，之后……，最后……。

### 5.1 先确认输入可用

```c
/* 学习注释：解释本块意图。 */
real_code();
```

解释真/假分支、写入对象、下一步和设计依据。
````

正文可以用中文段落解释因果，不必把所有内容挤在代码注释里。注释宜位于关键动作之前或分支内部，与原代码同级缩进。

## 4. 注释版源码的忠实性

学习注释只属于第5节Markdown，不写入产品文件，也不改变`source_snapshot`。保持原标识符、字面量、条件、括号、表达式求值顺序、分支、循环、break/continue/goto/return和条件编译。

不能：

- 给原本无超时的while添加timeout，让读者误以为原代码已有；
- 将`>`改成`>=`，把递减去抖改画成严格连续去抖；
- 因为代码看起来可以优化就重排语句，或省掉保护/失败分支；
- 用伪代码替换原代码却仍标为真实片段；
- 用“省略相同处理”隐藏实际不同的case或公共尾部；
- 根据未启用宏分支说明当前实际运行行为。

大函数可以分块引用，但每个实质逻辑必须在某一块解释，片段之间说明衔接。第1节仍必须保留完整原函数。

## 5. “为什么”的依据规则

| 标记 | 能写什么 | 不能写什么 |
|---|---|---|
| 【源码事实】 | 真实分支、调用顺序、已读取SDK定义与宏值 | 没读到的寄存器副作用或物理输出 |
| 【控制流推导】 | 早退后哪些语句不执行、循环何时退出 | 硬件异常必然导致具体器件烧毁 |
| 【设计意图推断】 | 有代码依据的合理工程解释 | 凭函数名编历史动机 |
| 【文档声明】 | 函数头/手册/规格写了什么 | 注释与活动代码冲突时用注释冒充现状 |
| 【待确认】 | 缺SDK/手册/实板导致的未知 | 用泛泛“待确认”代替可从源码得到的结论 |

## 6. 不同语句的重点

| 代码类型 | 要讲清楚 |
|---|---|
| 外设使能/Ready | 配置请求和状态确认的区别；谁改变Ready；未知时标未知 |
| 空while/轮询 | 等待什么、何时退出、是否有局部超时、卡住后哪些代码不执行 |
| 锁与临界区 | 寄存器写保护、线程锁还是IRQ屏蔽；DMA等是否仍独立运行 |
| 状态switch | 每个条件及动作；状态赋值后本次是否继续执行公共尾部 |
| 算式与限制 | 单位、正负、除法截断、中间位宽、溢出/饱和及上下限量纲 |
| 缓冲/ISR | 生产消费、发布时刻、抢占点、多次复核；检查存在不等于竞态已证明安全 |
| 单行getter | 返回值/副本/指针/软件镜像还是实际状态，以及返回后有效期 |

## 7. 反例

不合格：

```text
L141 执行语句：DDL_RCC_Unlock();
L143 执行语句：DDL_RCC_HSI_Enable();
L144 循环继续条件：DDL_RCC_HSI_IsReady() != 1U。
```

也不合格：

```c
DDL_RCC_HSI_Enable();  // 使能HSI
```

合格方向：

```c
/* 发出使能请求后仍须轮询就绪状态；调用返回不等于硬件已经就绪。 */
DDL_RCC_HSI_Enable();
while (DDL_RCC_HSI_IsReady() != 1U)
{
    /* 原代码没有局部时间退出；未就绪时后续切源不会执行。 */
}
```

随后说明Ready精确定义、启振最长时间和看门狗是否已启用，需要SDK、手册和调用顺序证据。

## 8. 检查与交付

工具可检查第1节标题/源码块、第5节标题/源码围栏及已知机械清单模式，**不能机械证明解释正确**。复杂初始化、状态机、中断和控制环必须逐函数读源复核。

复审记录至少包含`original_function_body_fidelity`、`code_explanation`、`annotated_source_fidelity`。仅复制函数头、只改标题、把通用注意事项贴到所有函数或把未知写成肯定结论，均不得认定合格。

## 9. 为什么必须先看完整函数

先展示完整函数，可以避免解释者只截取“看起来重要”的分支而漏掉公共尾部、早退、条件编译、故障清理和原作者注释。第1节承担证据固定，第5节承担教学解释；两者不能合并成一份被重新注释过的“伪原码”。

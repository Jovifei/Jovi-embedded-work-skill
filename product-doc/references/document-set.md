# 产品文档组合与正文深度

## 先决定受众

产品/测试/维护需要知道功能、条件、参数和可观察现象，不需要先看几百个函数；研发需要在依据处查函数和行号。默认是“当前软件实现说明”，不是替代销售认证规格书。用户有既定说明书结构时优先沿用，不静默换框架。

## 中型嵌入式产品可采用的七个专题

| 专题 | 要覆盖的实际内容 |
|---|---|
| 产品与主要参数 | 用途、接口、支持的模式/档案、当前启用和关闭项、主要限制、型号/版本冲突、未确认指标 |
| 上电与准备开始 | 初始化、可信采样、校准、开始资格、连续时间、额外等待、准备/预充、执行器接通、失败重试 |
| 业务阶段与档案 | 所有有效档案及单位；各阶段进入/退出、目标、限制、结束和再次开始；不同模式单列 |
| 调节与真正输出 | 所有限制共同作用，参考值如何变成控制请求；最小/最大/斜率、延迟、执行和物理结果的区别 |
| 故障停止与恢复 | 每项触发/确认/立即动作/执行器处理/锁定/恢复/人工操作；中断快保护与慢检查分开 |
| 通信设置保存升级 | 命令/字段单位、超时、受理与保存差异、换参数等待、掉电和无变化值、升级边界、长期运行 |
| 参数口径与验收 | 定义/使用冲突、哪些可引用、哪些是推导、哪些待测；按真实功能写待执行验收和发布限制 |

这是规划参考，不是必须七册。没有电池就不建电池档案；没有PWM就讲真实执行器；简单传感器可合并为三册。完整覆盖功能优先，不靠册数和页数充数。

## 每个功能模块按一段运行故事写

先说明设备处于什么情况、为什么做这件事；写清进入条件和数据；按实际动作解释判断/计算/等待/输出；说明成功后去哪；不满足、超时、故障和下一次尝试怎样处理。插入带参数的流程图和一个正常/一个失败或边界场景；无某项时说明依据。

“等100ms”还不够：是谁开始计时，必须连续满足还是累计，中途抖动是否重新计时，用新样本还是旧样本，最长多久，不满足时PWM/执行器是什么状态，都按当前代码写。

产品读者先看到“接通继电器”，依据中才出现状态名。不能把命令、GPIO输出、等待机械动作和触点实测混成一个“接通成功”。同理不能把串口ACK说成参数已落盘。

## 附件不是装饰

参数台账收录每个产品结论依赖的定义与使用处；多档参数表要覆盖所有有效档案，不只默认档；保护表写触发与恢复两套条件；验收表写边界值、名义时序和观察点，初始全部NOT_RUN。

给正文/图/表和源码使用处建立交叉引用。不要只把一份宏列表作为“产品说明”，也不能删掉异常路径只剩展示功能。

# 参数、推导和证据

## 先分清五种结论

| evidence | 中文含义 | 可以怎样写 |
|---|---|---|
| SOURCE_CONFIG | 源码默认设定 | 该源码定义为X；还要核对实际构建覆盖 |
| ACTIVE_LOGIC | 使用处实际判断 | 在已说明的状态/变体下，条件满足后执行Y |
| DERIVED | 可复算推导 | 根据列明的有效限制，必要条件为…；不是实测保证 |
| MEASURED | 已提供的实测 | 附同一硬件/固件/工况、方法、日期和报告，不扩大范围 |
| UNKNOWN | 资料不足 | 未提供或存在冲突，具体缺什么证据 |

“有个宏”不等于启用了功能，“当前代码默认”不等于目标工程实际编译。“注释说80%但宏和使用式是75%”应同时记录冲突，以已核对的活动表达式说明软件行为，不悄悄改文件。

## 每个关键参数的追踪链

定义/默认表达式 → 构建覆盖 → 实际使用位置 → 运行模式/档案 → 输入量的测量位置和处理方式 → 其他更严格的限制 → 输出动作 → 图表/正文结论。

台账至少填：产品名称和值、单位、语义类别、条件、原宏/表达式、定义路径和行范围、使用路径和行范围、证据类型、推导式和不确定项。源码哈希与编码写manifest；行范围必须落在这份文件里。`source`不必都是C文件：实测结论引用已提供报告；没有来源就UNKNOWN。

不得直接求值任意源码表达式或执行eval。条件编译和多处覆盖人工核对；未知分支明确标记。源码值在多处不同不能自动取最大的一个。

## 容易讲错的参数关系

- 开始检查门槛、准备阶段门槛、运行下限、某一降功率拐点和达到额定功率的必要条件，不是同一个电压。
- 连续功率/电流预算、阶段目标、软件跳闸点、硬件比较器点和器件绝对额定值分别列出。
- PV输入功率不是电池输出功率。代码中的效率估算系数不证明实测效率。
- 由功率/电压估算的电流不是独立传感器实际电流闭环。
- 平均值、峰值、原始ADC码和校准后数值不能互换；不把容差项写成测量精度。
- 计数次数、名义任务周期、硬件中断响应、最坏等待时间不同。说明从哪次事件起算，是否要新样本。
- 0、负数、极小非零值可能表示禁止或哨兵。不能为了方便解释把安全0抬到最小工作值。

## 满功率怎样解释：只作通用教学示例

假设一个虚构设备的输入预算为：

`P_allowed = min(P_rated, V_in × I_in_limit, V_out × I_equiv, P_stage, P_thermal)`

只有当源码真的使用这些限制且单位一致，才可以从它推导：达到额定输入预算至少需要`V_in >= P_rated/I_in_limit`、`V_out >= P_rated/I_equiv`，其余限制不更小，能源本身也足够。这个交集是必要条件，不保证设备一定输出额定功率。若效率、占空比能力、温度或电池阶段未确认，要继续列限制。

**上式不是本skill对任何新项目的默认模型。** 实际代码用其它公式或输入量时必须重建推导。示例数据不得沿用此前MPPT项目的300W/10A/5A。

## 故障和恢复必须成对

写触发比较符（严格>还是>=）、平均/峰值/原始值、确认时间、运行条件、立即停什么、延后停什么、谁锁住；再写恢复条件、持续时间、谁清证据、自动还是必须人工重新开始。故障消失不等于立即允许重启，软件锁清除也不等于PWM实际恢复。

## 不得从源码造出的产品承诺

绝对输入范围、效率/纹波/精度、温升、待机功耗、短路和反接耐受、触点寿命、IP、EMC、安全认证和长时间可靠性，都需要对应规格或实测证据。没有资料时在主要参数页显式待确认，不藏在最后一页小字。

# Prj_ZL 工程目录与构建引用整理

**Version: V0.2.1**

先确认本轮目标根目录、基线和允许的目录变化，再移动文件并更新实际构建引用。保持产品参数、代码语义、外部 ABI、目标选项与部署约定。目录名称、文件数量、模块划分与函数位置由当前工程决定，已有清楚结构时优先局部整理。

本技能规定归属判断、引用完整性和验证方法，不提供所有项目必须采用的目录树。具体路径和代码仅作为明确标注的例子；只有本次需求或项目合同采用时才成为该项目要求。Keil XML 字段与检查器路径属于工具接口，不能据此推导产品源码的布局。

## 1. 执行边界

- 区分目录迁移、业务重构、BUG 修复和功能变化。本 skill 负责文件归属与构建路径；混合文件中需要拆函数、换接口或改调度时，作为明确的结构工作交给 `code_wrt`，不能藏在搬目录中。
- 先读现有 AGENTS/CLAUDE、README、计划、目标工程与版本记录；以当前用户要求和已批准合同确定范围。已有授权覆盖的迁移、验证和提交继续执行，不重复请示。
- 用户只指定一个子工程时，只改该子工程及为完成迁移所必需的共同引用；不顺便整理其他子工程。发现另一目标受影响时说明事实及最小处理范围。
- 保留用户已有未提交改动。不自动 reset/clean、覆盖文件、删除历史资料或重排无关代码。Git 提交/推送按用户已经给出的仓库与范围授权执行。
- 不把旧项目的目录、文件、任务数量或供应商库选择带入新工程；未采用技能例子的名称或结构不构成验收失败。

## 2. 建立文件与构建映射

用 `rg --files`、`git ls-files` 列出目标根内源码、头文件、汇编、工程、链接配置、脚本和依赖。记录每个活动目标的源文件成员、包含路径、宏、器件、输出名及前后构建步骤。

至少形成：

| 旧路径 | 新路径/保持 | 实际职责 | 所属 target | 引用位置 | 迁移验证 |
|---|---|---|---|---|---|
| 待定文件 | 先据源码分类 | 应用/驱动/启动/共享 | 明确工程与目标 | XML/include/脚本/文档 | 存在/同一成员/待构建 |

区分活动源码、SDK、生成文件、历史备份和测试替身。不能仅按文件名或旧目录猜归属；混合职责无法靠移动解决时保留并记录后续拆分。

## 3. 按职责判断归属

| 职责 | 归属依据 | 注意事项 |
|---|---|---|
| 产品业务 | 业务决策、产品状态、公共业务接口及实际调度协作 | 归属实际责任方，不靠聚合头掩盖混合职责 |
| 硬件适配 | 外设访问、板级配置及与目标硬件绑定的实现 | 依据依赖和行为判断，不仅看文件名 |
| 启动与平台支持 | 向量、时钟、设备初始化及供应商移植层 | 保留供应商约定与链接归属，不因目录对称移动 |
| 跨目标共享 | 确由多个目标使用且须一致的格式、常量或算法 | 核对真实消费者与版本关系，不创建杂散全局量集合 |
| 构建与部署 | 工程文件、链接配置、构建和部署入口 | 保留其实际路径基准、工作目录和外部消费者 |
| 文档、测试与产物 | 说明、独立验证代码及可追溯结果 | 测试替身不得误编入产品；历史产物不冒充本版 |

这些是判断维度，不要求各建一个目录或文件；同一文件是否拆分取决于当前职责边界及授权范围。

**目录举例（非规范）：**某项目采用 `app/src`、`driver/src`，另一项目采用 `services/`、`platform/`，也可以沿用既有组件结构。这里只说明“路径可以不同而职责清楚”；不要求迁成其中任何一种，也不要求为了凑目录而拆文件。

中断入口可能受供应商和启动链接合同约束。迁移时保留实际处理上下文、回调和服务方式；目录调整本身不授权改变调度。文件移动后仍存在不符合本项目隔离目标的硬件依赖时，分别报告“目录迁移完成”和“隔离目标尚未完成”。

## 4. 执行迁移

1. 在已明确的映射下创建必要目录。已跟踪文件优先 `git mv`，新增/未跟踪文件使用适合其状态的移动方式；记录改动，保留原有用户内容。
2. 同步实际构建系统中的受影响引用；使用 Keil 时包括 `.uvprojx/.uvoptx`。同时核对链接、构建后处理、烧录/升级脚本、CI 和相关文档。只改指定目录但忽略它的真实构建消费者不算完成。
3. 既有头文件引用能继续正确解析时保持；相对路径或大小写必须修改才能等价解析时，做最小修正并记录。不得坚持“不改 include”而留下失效引用，也不得借机改条件编译或宏语义。
4. 保持目标的源文件成员、文件级编译选项、宏、器件、链接区域、库版本及优先级。替换路径时按实际路径组成处理，不能全局替换同名目录而波及依赖或无关目标。
5. 只有确认目录为空且所有活动引用已处理后才移除旧空目录；历史路径与 SDK 的合法命中记录为允许残留，不为达到零搜索结果删除资料。

## 5. Keil 路径和命名

涉及 Keil 工程时，修改前读 [Keil 路径与构建核对](references/keil-paths.md)。对每个受影响 target 分别核对 FilePath、IncludePath、ScatterFile、文件级选项、输出名、前后构建和下载脚本；保留 `.uvoptx` 的调试设置。其他构建系统采用其对应配置语义。

- 项目文件中的相对路径按对应项目/工具实际基准解析，不按仓库根臆测；动态路径、设备包和外部依赖单列。
- 工程名、输出名及其后缀可能承载发布或烧录约定。仅在用户要求或本轮明确包含重命名时修改，不能凭名字外观判断可以删除。
- 改工程文件名、TargetName、OutputName 是不同操作。需要改变哪些就改哪些，同步实际消费者；不能假定 AfterMake 的所有写法都会自动跟随。
- 厂商 SDK/闭源库是构建依赖，不把依赖目录整体加入忽略。保留现有可复现获取方式、版本/哈希和许可证要求。
- `.gitignore` 只按实际规则补本地产物。用户已版本化的发布镜像、烧录资源、工具和有意跟踪的配置不能擅自停止跟踪。`.uvoptx` 是否纳入版本管理沿用项目约定。

## 6. 验证

按本轮风险完成以下检查；缺工具或依赖时区分缺失原因，不据此宣称代码逻辑有 BUG。

1. 检查 `git diff --check` 和变更范围，核对旧→新映射，确认无覆盖和漏移。
2. 核对实际构建配置；Keil 工程解析项目 XML。比较每个 target 的成员、宏、关键选项和链接范围是否前后等价；检查重复编译、大小写、失效 include、误加测试替身和遗漏回调/IRQ 实现。
3. 对迁移后的 Keil 项目使用本技能的只读路径检查器；参数替换为实际工程文件，示例路径不要求存在于项目中：

   ```bash
   python3 <skill-dir>/scripts/check_keil_paths.py path/to/project.uvprojx
   ```

   退出 0 仅表示检查到的字面路径通过；退出 2 表示路径/解析问题；退出 3 表示动态或当前主机不可解析的路径需要人工核对。输出不是目标编译结果，也不证明启动向量或业务功能正确。
4. 在可用的匹配工具链进行本版全量构建。没有工具链/依赖时仍完成静态核对，记录 `BUILD_NOT_RUN/BLOCKED` 和复现命令，不拿旧 map/旧镜像代替。非 Keil 工程按其实际构建系统核对，不制造 Keil 文件来满足检查器。
5. 若涉及调用链、硬件访问、复位/启动或部署变化，交叉应用 `code_sc/code_wrt` 的适用检查，并列清所需板测；纯目录移动不擅自增加业务改动。
6. 同步目录说明、构建入口、版本/变更记录和受影响的学习资料，已授权工作完成后继续交付。

## 7. 输出

报告实际目标身份、文件映射和范围、已保留的构建合同、修改的引用、每项验证结果、未执行项及原因。明确区分：

- 文件与路径迁移是否完成。
- 应用/驱动职责与硬件隔离是否真正完成。
- 本版目标构建是否执行。
- 实板或部署行为是否执行验证。

不把“新目录已经存在”“搜索不到旧路径”“XML 能解析”写成整个重构已验收。

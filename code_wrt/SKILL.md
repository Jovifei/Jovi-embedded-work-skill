# Code WRT

**Version: V0.4.3**

以已确认需求和实际工程为依据，完成可验证的嵌入式代码修改。保留合理实现、产品参数和外部合同，用必要的模块、清楚的职责和简短的调用关系解决问题。

## 1. 固定范围，沿用已有授权

1. 区分方案、只读审核、注释整理和实施；先读本次指定源码、构建入口及必要调用链。保留用户已有的工作区和暂存修改。
2. 分别标识**原工程/在役基线、参考工程、当前修改版**。记录工作树、branch/ref、HEAD SHA、dirty files、目标/配置、依赖和当前构建证据；工作树未提交时用内容 hash 绑定证据。
3. 写清本批目录、必须保留的功能/参数/ABI、已允许变化、可用验证条件和交付范围。核对 todo、版本记录与实际源码，冲突单列。
4. 已授权的阶段计划继续执行；不因模板、技能门禁或每个小批次重复请求许可。只有未确定的产品行为、真实范围扩大或关键取舍才提出具体问题。
5. 已确认且处于授权范围的 BUG 应修复，不为等价保留缺陷。只授权等价整理时发现行为问题，登记反例和独立修复范围，先完成能证明等价的部分。
6. 参考工程只提供候选实现。逐项说明原问题、改善、硬件/时序前提、保留参数和证明方式，不能整包替换当前产品或顺带迁入阈值。
7. 用户授权对仓库、操作和范围在本会话内持续有效。先核对已有授权再进行暂存、提交、分支、合并或推送；没有对应授权时完成代码与验证，不擅自发布，也不反复索要已给出的授权。

按以下四类分别登记；一个批次可以包含多类：

| 类型 | 要求 | 本批证据重点 |
|---|---|---|
| 结构整理 | 保持约定的可观察行为和调用合同 | 函数映射、调用时点、初始化/IRQ、编译链接 |
| BUG 修复 | 给出触发条件、因果链、最小安全修复 | 修复前反例、修复后结果、相邻路径 |
| 已批准功能 | 写明新行为、兼容和部署影响 | 正常、边界、失败、恢复、旧配置/客户端 |
| 性能/空间优化 | 先确认瓶颈，局部优化 | 同条件前后 map、耗时、栈及功能对照 |

启动、首拍/斜率、CBC、预充、Demo、配置或 OTA 行为变化不能只登记为“结构整理”。

## 3. 职责先清楚，文件保持克制

- 一个事实、业务决策或可变状态有一个明确 Owner；消费者不维护可自行修正的“当前值”副本。区分事实生产者、历史计算和安全复核。
- Layer、Owner、Caller/Callee、Timing、输入/输出单位、状态与硬件副作用用于描述实际合同；它们不要求各建一个文件、DTO、manager、service、coordinator 或 wrapper。
- 优先沿用工程目录及真实 Owner 的已有 `.c/.h`。新增模块需有独立职责、状态归属或验证收益；不机械移动 SDK、驱动和工程。
- main 负责初始化、时间、节拍、任务顺序和系统健康；前台默认串行。顶层 task 由调度者调用，不由同级 task 嵌套。允许模块通过简单、单向、窄语义的普通接口提出请求。
- 六类职责 `sample / charge / protection / output / debug / mmi` 适用于已明确采用它们的工程，包括当前 C300；不是所有嵌入式产品的强制目录，也不是只能有六个 C 文件。
- 公开接口只暴露调用者需要的内容。优先现有只读快照或明确参数；确有跨边界稳定合同再用窄 DTO，不为形式新增数据副本或复制供应商 ABI。
- 驱动拥有寄存器、SDK 类型、引脚、通道、NVIC、Flash 和 CPU 临界区细节；应用使用逻辑通道、物理量及明确结果。驱动不依赖业务 ctx，应用公开头不无故泄漏整套 MCU SDK。
- 避免互相写内部状态和反向依赖；事件、命令或既有 main 编排均可解决实际协作，不必引入消息总线或新协调模块。
- 遥测和诊断读取快照、限量发送，不通过调试 setter 改正常策略；有明确控制语义的用户命令归相应应用职责。

跨模块修改前，按本批填写必要行即可：

| Owner/职责 | 调用者 → 被调用者 | 上下文/时机 | 数据、单位、有效期 | 状态/硬件副作用 |
|---|---|---|---|---|
| 实际文件或既有模块 | 真实调用链 | ISR/前台/任务/事件 | 来源、产物、失效条件 | 允许写入者及失败结果 |

## 4. 完整接口与真实数据合同

1. 改 API 时列完整返回类型、函数名和形参类型/顺序/const/方向，说明单位、合法范围、生命周期、alias、执行上下文、副作用与失败结果。不要只给函数名或 `...`；沿声明、定义、回调、所有调用、测试和工具同步。
2. `ctx` 是该 Owner 的可变状态，`in/snapshot` 是规定时刻的输入，`out` 是产物，`cmd/event/pending` 分别说明命令、事件和待消费事实。按实际调用域判断并发，不因“可能多线程”就加锁。
3. 区分候选、批准、已提交设定和硬件实际生效。CCR、MOE、GPIO ODR 或库 Duty 都不能未经核对冒充实际物理输出。
4. 事实、资格、命令和否决分别说明来源/时点；多个 bool 有业务关系时列语义矩阵。合法零、未启用、无效和停机不共用未说明的数值含义；外部既有编码保持兼容。
5. 初始化、重置、停机、故障、维护和换档列清保留/清零/失效状态。积分、滤波、序号去重、故障代次和时序记忆可能是必要内部状态，不因不导出就删除。
6. 预览不得通过指针别名修改正式状态；一次正式更新的时点和次数明确。已存在的错误写入按 BUG 范围处理，不偷换等价基线。
7. 仅在收益和消费者明确时预计算或缓存。按输入、模式、档案、目标、限制来源、校准、采样身份/时刻/有效性和故障代次定义更新/失效；序号相同或最终最小值相等不足以证明命中。
8. 数值等价需核对整数提升、中间宽度、符号、乘除顺序、截断、饱和和计时回绕。浮点改定点或改公式另列范围。

## 5. 下行命令、上行事件和紧急关断

**普通命令通过应用调用明确驱动接口；硬件异步事件通过驱动 ISR 发布有界事件/快照供前台消费。** 不要求普通调用通过中断。

- 触及异步链时核对外设使能、NVIC、startup 向量、强 handler、驱动处理、事件/缓冲和前台消费者。weak `Default_Handler` 不能替代已启用 IRQ 的实现。
- 驱动 ISR 可读清标志、搬运数据、做有界组帧、记录时刻/序号和执行紧急电气关断；复杂状态机、MPPT、Flash 写入和阻塞日志留在前台。硬件等待需有预算、超时和安全失败路径。
- 回调明确 ISR/前台上下文；可使用已有注册、弱符号或 pending/take 机制。ISR 回调只承担该上下文允许的短操作，不能执行完整业务/输出状态机。
- **前台正常 PWM/功率继电器由 output 最终审核并通过驱动提交；硬件保护和驱动 ISR 立即关断，不等待前台，也不调用完整 output 状态机。** 非功率 GPIO、Flash 等按各自 Owner，不强塞进 output。
- 同轮命令、停止/维护请求、保护判定和恢复资格必须先纳入最终功率提交。output 后的任务不得再用旧候选或旧请求打开功率。
- 恢复依据当前故障、采样有效性、维护状态、候选/事件代次和硬件资格。保留有目的的写前、写后及恢复中断后的复核；不能去重掉不同时间点的现场检查。
- 重新发波需核对物理 OFF、实际关断值、自然更新、首拍、斜率及旧算法记忆。新增首拍/斜率属于行为变化，依据已批准或已确认缺陷合同实施，不能把别的工程数值直接迁入。

## 6. 采样、时间、健康与持久化

- 样本记录来源、单位、序号、采集时刻、有效性和校准条件。只有新采集刷新新鲜度；电流、功率、极值和计数属于相容窗口。换平台、校准、滤波改变后按合同失效历史与候选。
- 超时/冷却/上报用单调时间或实际 elapsed；连续有效证据用新样本次数；积分有明确有效跨度及缺样策略。漏服务不补造样本，不无限使用旧功率补积分。
- 喂狗观察关键生产者与控制流程在规定窗口内的进展；主循环转动不等于健康。启动/校准/维护/Flash 有明确预算，时源不能用自身已停走的时间证明自己健康。
- 配置先校验完整候选，按合同持久化并验证后发布有效版本；失败不留下半套档案。区分记录缺失、有效旧值和介质损坏，不能清空配置掩盖失败。
- UART 同时校验上限、字段间长度关系、CRC/校验和、完整帧边界及生命周期；发布帧不能被后续半帧覆盖。ACK 入队不等于硬件发送完成，保护关断不等待 ACK。
- OTA 记录准备、持久化、擦写、校验、完成提交、结果发送和跳转顺序。持久化失败不得继续依赖它的破坏性操作；覆盖首装/工厂烧录、断电恢复、重入、回退及实际 APP/BL 组合。
- APP/BL 真正共有的分区、长度、记录格式和校验采用同一来源。重构不自动授权更新 Bootloader 或改变部署格式。

## 7. 小批实施并验证当前结果

1. **写前**：固定基线、四类修改和保留合同；读相关 reference；核对真实调用路径、Owner、接口与失败后果。
2. **实施**：复用合理实现，按授权小批修改；同步活动消费者、工程引用、测试夹具和必要注释。不要靠恢复旧接口满足过时 fixture。
3. **写后**：对最终 diff 检查调用/数据/所有权、状态推进次数、模式分支、硬件复核位置、公开头、IRQ 和真实消费者。合并结果是新版本，父分支 PASS 不继承。
4. **验证**：选择能暴露实际风险的行为反例、Host 检查、预处理/目标构建或板测；不要为可逆低影响改动新增无意义测试。必要实板条件缺失时继续其他已授权工作，并保留放行条件。
5. **收口**：证据绑定最终 SHA/内容 hash、目标、defines/includes、依赖、命令/退出码和结果含义。失败时保留首个差异，不改期望或版本掩盖；回退仅处理本批修改。

各证据独立标记**通过、失败、未执行、受条件阻塞、已知限制**。Host、目标编译链接、CI、架构检查和实板分别报告；缺板测是证据缺口，不自动认定代码 BUG，也不能伪造实板 PASS。只要适用必要门禁未通过，就不要宣称该项已放行；可以明确“实现完成，硬件验收待补”。

按项目策略更新受影响的固件版本、修改说明、任务表、接口/参数和学习资料；纯注释/文档不自行升固件版本。技能版本只在技能维护时更新。若约定知识库/Obsidian 同步，实际完成后才报告成功。

## 8. 完成报告

按改动规模给出本批目标、四类变化、关键 Owner/调用/完整接口变化、实际验证及剩余事项；小改用短表，不强制十一份报告。较大批次使用本地 [记录模板](references/scope-and-verification.md#批次记录模板)。

必须说明最终源码身份、完成与未完成范围、未执行条件、固件/文档版本处理，以及需后续验收的时序、硬件或部署项目。不得用旧日志、脚本退出 0、能编译或看门狗未复位证明所有功能正确。

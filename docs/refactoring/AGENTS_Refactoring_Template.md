# 合并、移植与重构执行原则（可合并模板）

版本：v1.2；日期：2026-11-25。

完整说明：[Embedded_Refactoring_Principles.md](Embedded_Refactoring_Principles.md)。将本模板与目标项目已有规则合并，保留有效约束；不通过覆盖文件消除要求。

## 1. 适用边界

本模板约束判断和执行方法，不指定具体函数、文件、目录名称、模块数量、芯片、库、参数或调度结构。具体方案依据当前项目与本次需求确定。例子只用于解释原则，其实现不得自动成为约束。

已知信息直接填写，不为填表重复询问。具体文件和函数映射在本项目方案中记录，不回填为通用要求。

## 3. 行为与变更范围

以安全和已确认需求为前提，保留正确实现。结构整理、缺陷修复、批准的功能变化、性能或空间优化分别说明，避免将实际行为变化描述成单纯搬迁。

已有授权覆盖的阶段继续执行；只有范围或关键产品选择未确定时才提出具体问题。保留用户未提交工作，不擅自覆盖、清理或改动无关工程。

## 4. 合并与吸收

分别识别接收方、参考来源和最终结果。逐项判断收益及适用前提，分别决定是否吸收实现、参数、算法、协议和部署方式，不整包继承来源工程。

冲突同时检查文本和语义，包括职责、状态、接口、调用时点、构建及数据格式。合并结果重新复核，父版本通过不等于最终版本通过。

## 5. 职责、文件和接口

按职责、状态生命周期、硬件依赖和验证收益组织，沿用合理结构。不要以固定文件数量、模块名或层级作为验收目标，也不为转发调用堆叠包装。

关键状态、规则和副作用有明确归属及协作方式；多个合法执行路径需要一致的仲裁。保留必要适配、外部约定和不同时间窗口的安全复核。

移动、改名或调整接口时同步真实消费者、全部相关构建目标、链接、测试与部署引用，核对大小写、相对路径和外部布局。文件迁移与职责解耦分别验收。

## 6. 硬件、调度与并发

将硬件相关细节集中到明确边界，保持接口含义稳定。按当前执行模型选择同步调用、回调、事件、缓冲或队列；不强制所有交互通过中断，也不为重构更换调度框架。

说明异步上下文、数据寿命、完成含义和失败处理。依据实时要求确定优先级、执行预算与延后工作，不套用其他项目的数值。

检查共享访问、事件交接、缓冲所有权及检查到提交之间的竞争。临界区保存并恢复原状态，保持有界；可见性标记不能替代一致性。

## 7. 数据、时间和安全行为

说明数据来源、单位、有效性和必要时间关系；不机械增加字段或镜像。区分事实、请求、许可、提交与物理结果。状态变化时明确旧请求、缓存及历史数据的有效范围。

实际时长与事件次数分别处理，定义缺样或延迟执行策略。健康监测反映约定工作是否在预算内推进，活性与截止时间分别验证。

涉及危险动作时，正常控制有明确许可和仲裁，紧急保护满足响应时限，恢复不能被旧请求绕过。检查启动、停止、故障、复位与重新启用；具体动作和阈值由当前项目给出。

## 8. 配置、通信和部署

只检查项目具备或本次要求增加的能力，不从例子添加功能。需一致生效的数据完整发布，失败保留或恢复到约定有效状态。

通信同时校验边界、字段关系和数据寿命，准确区分接收、执行、发送及确认。共享格式保持一致，涉及存储或升级时验证实际使用的失败恢复、初次部署和兼容路径。

## 9. 实施、验证与交付

先明确目标与验证方法，再按可核对范围实施。小改动简短记录，复杂或高风险变化增加对应检查，不机械增加文档、测试或审批步骤。

注释解释真实代码；纯注释保持代码语义。优化提供实际收益，核对数值、布局、缓存和时序等价条件。

分别报告静态检查、主机测试、目标构建和实物验证的状态，证据对应最终内容。缺少条件时完成其余可做工作，明确未测项，不伪造通过结论。

问题按事实、触发条件、因果链、影响、修改方向和验证标准描述；区分遗留、新增、批准变化和证据缺口。交付同步受影响的既有文档及版本记录，保留必要部署和回退说明。

本模板不授权修改其他项目，不要求安装特定辅助技能，也不保证现有代码已经符合这些原则。

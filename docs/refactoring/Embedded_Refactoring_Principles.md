# 嵌入式工程合并、移植与重构原则

版本：v1.2；日期：2026-11-25。

## 1. 本文规定什么

**在已确认需求和安全边界内，保留应保留的行为，以清楚的职责、尽量简单的实现和与风险相称的验证完成工程变化。**

本文规定判断和执行原则，不指定某个产品的函数、文件、目录名称、模块数量、芯片、算法库、参数、调度模型或中断优先级数值。具体实现从当前项目和本次需求中确定。

原则应能在更换产品、硬件、编译器、目录布局或函数名称后继续成立。如果一条规则只有放回某个旧工程才说得通，应提炼出它要保护的性质；余下内容属于项目约束或举例。

| 内容层次 | 回答的问题 | 使用边界 |
|---|---|---|
| 通用原则 | 为什么这样判断，必须保持什么性质 | 可跨项目复用，不携带具体实现清单 |
| 项目约束 | 本项目必须保留或允许改变什么 | 来自本次需求、有效规范和当前工程证据 |
| 实施方案 | 具体改哪些对象，怎样调用和验证 | 在目标项目中制定，可包含真实文件、函数与数值 |
| 举例 | 一项原则在某种条件下怎样应用 | 只解释推理；名称、数量、路径、数值和方案均不自动成为要求 |

举例不能新增用户需求，不能替代芯片或协议依据，也不能反过来决定项目必须怎样拆模块。本文中的说明性例子集中在第 15 节。

## 2. 先明确目标、基线和授权

开始前明确实际目标、修改范围、保留项、允许变化、可用验证条件和交付要求。已有信息直接沿用；缺失且影响关键取舍的内容明确列出，不能从参考工程或旧对话猜出默认答案。

合并或吸收实现时，分别标识接收方基线、来源版本、共同祖先（适用时）和最终结果。源码、构建选项、依赖与验证记录必须能对应到具体版本。未提交内容可用文件内容标识固定身份。

先核对已有修改、暂存内容和生效的项目规则，保留用户工作。不得用覆盖、清理或重置掩盖冲突。已授权阶段验证后继续推进；仅在范围或关键产品选择未确定时提出具体问题，不为执行同一计划反复索要许可。

具体文件和函数清单写入该项目的实施记录，不固化到本通用规范中。

## 3. 区分修改性质，保持行为说明真实

| 修改类型 | 主要原则 | 需要的证据 |
|---|---|---|
| 结构整理 | 调整组织与依赖，保持已约定的可观察行为 | 职责和调用关系对照、状态推进与副作用、构建引用 |
| 缺陷修复 | 针对已确认问题作最小且安全的修正 | 可达触发条件、因果链、修复前反例及修复后回归 |
| 已批准功能变化 | 实现明确的新行为，处理兼容与失败路径 | 正常、边界、异常、恢复及旧数据或客户端影响 |
| 性能或空间优化 | 依据实际瓶颈，避免以复杂度换取未经证实的收益 | 相同目标与选项下的资源、时序和行为对比 |

一个批次可以包含多类修改，但应分别说明。行为包含输入输出、调用时机、失败语义、故障响应、状态恢复和持久化效果，不只指正常稳态结果。

已经确认且处于修复范围的缺陷应当修复；不能以“保持等价”为由继续保留。只获授权做等价整理时，登记行为问题并完成可证明等价的部分，不把修复悄悄混入目录或注释调整。

## 4. 合并与参考实现吸收

以需求满足程度、可靠性、复杂度、可验证性和维护成本判断是否吸收。代码较新、行数较少或来自运行过的产品，都不能单独证明它更适合目标工程。

每一项吸收应回答：当前问题是什么，来源实现改善了什么，依赖哪些硬件或软件前提，目标工程保留什么，以及怎样验证。实现、参数、算法、协议和部署方式分别作选择，不整套继承参考工程的假设。

合并冲突不仅存在于同一行文本，还可能存在于职责、状态含义、调用次数、接口、配置、构建成员和部署格式。文本无冲突不等于语义兼容。解决冲突时沿真实调用和数据关系核对，不仅按“保留较新的一边”处理。

合并结果视为新的审查对象。重新核对接口及其消费者、初始化与退出路径、异步交接、目标配置和相关测试；父分支各自通过不能直接证明合并结果通过。保持必要的回退点和变更可追溯性。

## 5. 按职责组织，控制结构复杂度

模块边界由独立职责、状态生命周期、硬件依赖、变化原因及验证收益决定。文件数量、任务数量和命名形式不是重构质量指标。

每项关键业务规则、状态和副作用有明确归属；允许存在经过定义的多个写入者，但必须说明协作、仲裁和一致性，避免不同位置各维护一份可自行修正的“真实状态”。

优先保留现有合理组织。只有职责独立或变化边界确实需要时才拆分；短小转发、重复状态和机械层级没有收益时应减少。相反，必要的适配、稳定接口、安全复核或硬件时序步骤不能仅因代码短或表面重复而删除。

职责划分不强制一项职责对应一个文件，也不要求建立同名的任务或数据结构。若本项目另有明确文件组织要求，在项目方案中落实并说明原因。

## 6. 文件、构建与接口迁移必须完整

移动或改名要覆盖真实引用，包括编译成员、包含路径、链接配置、启动入口、生成步骤、测试、打包、烧录及其他实际消费者。检查大小写、相对路径基准、多个构建目标和文件级选项。

保留仍有效的供应商约定、依赖版本、许可证、外部接口、二进制布局和发布名称。确需改变时，连同受影响消费者和迁移办法一起处理。既有布局清楚可用时，不为套用示意目录而重建工程。

声明、定义、回调、调用者、测试替身、接收端与文档在适用范围内同步。清理旧符号时区分活动引用、外部兼容名称、历史材料和生成内容，不以“搜索结果为零”作为删除全部记录的理由。

文件搬迁只能证明位置改变；职责是否分离、硬件依赖是否隔离，需要分别从依赖、调用和状态访问取证。

## 7. 应用与硬件边界以迁移需要确定

将易随硬件变化的操作和依赖集中到明确边界，向使用者暴露稳定、含义清楚的接口。避免业务逻辑无必要地依赖寄存器、引脚、厂商类型或底层时序细节，也避免硬件实现反向操作业务私有状态。

控制请求和异步事件分别设计。同步接口、回调、事件、缓冲、队列等方式按当前调度和实时要求选择；不要求所有调用经过中断，也不要求为事件引入统一框架。

每个异步接口说明执行上下文、数据寿命、完成含义及失败处理。中断内能执行哪些操作，由截止时间、最坏耗时、共享数据和可调用接口决定；需要延后的工作交给适合的执行上下文。

保留合理的裸机、任务调度或实时操作系统模型。换芯片时重新核对处理器能力、工具链、库接口、内存布局及驱动时序；源码分层不能代替这些适配证据。

## 8. 数据、状态和接口含义清楚

输入输出应说明单位、范围、有效性、来源、必要时刻及生命周期。采用何种字段或结构表达由项目决定，不能为满足表格机械增加镜像状态。

区分事实、请求、许可、候选、已提交操作和已观测结果。返回成功应符合接口声明的含义；“已达到目标”与“这次刚发生变化”可以是不同的合法约定，应由真实调用者决定。

初始化、停止、故障、恢复、模式变化和配置变化应明确保留、清除或失效哪些状态。旧请求或旧计算结果是否还能使用，必须依据其有效条件判断。

对预览、只读接口和缓存检查真实副作用与依赖。通过指针间接写状态仍然是写入；缓存必须覆盖影响结果和使用资格的条件。内部积分、去重或事务记忆有实际用途时，不因未对外输出就删除。

数值整理核对类型提升、中间宽度、符号、截断、饱和、运算次序和回绕。单位相同或最终数值偶尔相同，都不足以证明两种计算等价。

## 9. 时间、并发和运行健康分别验证

超时及实际时长使用可证明的时间依据；连续事件或有效样本条件使用对应次数。固定周期只有在周期得到保证时才能替代实际时间。延迟执行不能补造不存在的事件或样本。

统计与积分明确数据覆盖的时间范围以及缺失数据策略。旧数据重复读取不变成新数据，长时间缺样不能无条件用最后一个值补算。若系统监测运行健康，应观察要求监测的工作是否在预算内推进，而不是只看某个循环仍在运行。

按实际可发生的抢占、嵌套和共享访问分析竞争。核对事件产生、取出、清除及再次到达的交错；核对多字段快照、缓冲交接和检查到提交之间的窗口。可见性标记不能代替原子性和一致性设计。

优先级和临界区服务于明确的实时要求，不设跨项目通用数值。临界区保存并恢复原状态，执行时间有界；检查锁顺序、饥饿和优先级反转等适用于当前调度模型的问题。运行活性与满足截止时间分别给出证据。

## 10. 涉及危险动作时保持安全路径

正常动作具有明确的许可、仲裁和执行职责；紧急保护在要求的时限内生效，不能因统一接口或归并文件而被普通工作阻塞。

不要求所有硬件写入位于同一个函数或文件。正常控制与硬件保护可以由不同路径实施，但必须验证其优先关系、交错以及故障后的恢复资格。

核对首次动作、稳态运行、停止、异常、复位和重新启用。保护发生后，先前的请求或正在进行的提交不得未经核实地抵消较新的否决。保留对不同时间窗口有意义的复核，不按表达式相同机械去重。

控制计算、软件命令、驱动设定和物理结果分别取证。改变驱动方式、限制、启动或恢复时序，即使计算库未换，也应重新评估动态行为。具体关断方式、限制和测量标准由本项目硬件与需求提供。

不涉及危险执行器的工程，不为套用这一节新增功率控制或保护模块。

## 11. 配置、通信和部署按适用范围处理

需要一致生效的一组配置按完整版本更新，失败时保持或恢复到约定的有效状态，不暴露半套数据。参数与模式是否独立配置、默认值怎样选择、何时保存，由需求确定；不能从举例引入额外模式或设置入口。

涉及持久化时，区分数据不存在、版本不兼容、写入失败和介质异常。保存完成标记、计数和索引应与真实成功条件一致，验证关键失败点和恢复路径。

涉及通信时，同时检查容量边界、字段关系、校验和数据寿命。请求被接收、操作完成、结果入队、发送完成和对端确认是不同事件，依协议给出准确语义。

多个程序或设备共享数据格式时，保证定义和实际消费者一致；可以采用共同来源或可靠的一致性校验，不强制建立特定名称的共享目录。

涉及升级或启动链时，检查实际使用的初次部署、更新、失败恢复和回退路径。若改变完整性判据或镜像格式，配套工具与兼容组合一并交付。不具备某项能力的项目，无需为满足本规范新增该能力。

## 12. 可读性、注释和优化

名称说明实际职责、对象和结果，沿用项目一致的习惯；不强制跨项目统一前缀或后缀。注释解释接口约定、前提、非显然原因、失败与恢复，不把期望行为写成已经实现的事实。

注释整理、格式整理、布局变化和逻辑变化分别界定。纯注释修改保持代码语义；格式或布局调整核对作用域、预处理、控制体绑定和外部布局依赖。发现真实缺陷应报告或按已有修复授权处理，不能只改描述掩盖问题。

减少重复计算前核对输入身份、状态、副作用、调用时机和数值运算。优化缓存或数据布局时提供实际收益及失效规则；不以代码行数、函数数量或主观感觉代替资源与时序证据。

## 13. 分阶段执行与验证

| 阶段 | 工作重点 | 进入下一阶段的依据 |
|---|---|---|
| 明确范围 | 固定基线、保留项、允许变化和验收目标 | 关键取舍已明确，缺口有记录 |
| 制定方案 | 描述职责、接口、行为变化与风险 | 方案能解释为何这样改，以及怎样验证 |
| 小批实施 | 完成一个可核对的变化范围 | 受影响引用和必要验证同步完成 |
| 集成复核 | 审查合并后的实际内容和交界 | 关键不一致已处理，证据对应当前版本 |
| 交付验收 | 更新受影响文档与产物 | 完成项、未测项和后续放行条件清楚 |

这些阶段是工作顺序，不要求分别建立文件或重复审批。小改动可以简短记录；复杂改动才展开所需细节。

验证深度与风险相称。优先选择能区分正确与错误行为的反例、边界及失败恢复检查；不堆只复述实现的测试。机械低影响修改不强制完整板测；涉及实时、硬件、安全、持久化或部署变化时补相应证据。

静态检查、主机测试、目标编译链接和实物验证分别报告通过、失败、未执行或受阻。缺少某项条件时继续完成其余已授权工作，但不得把缺失证据写成验收通过。修改后证据需对应最终内容，不能直接沿用旧版本结论。

## 14. 审核、记录与交付

问题说明当前事实、可达条件、因果链、实际影响、位置、复现或推导、最小修改方向和验证方法。区分遗留缺陷、本次引入、批准的需求变化及证据缺口。

优先级依据影响、可达性和已有使用证据确定。结构偏好、函数长度、文件数量或缺少一份测试记录都不能单独证明严重故障；已经证实的问题也不能被一次测试通过抵消。

交付随范围提供实际变更、源码身份、依赖与构建条件、验证结果、未关闭事项及必要的部署或回退说明。只同步受影响且约定需要维护的说明、图表和学习资料，遵守现有文档组织。

区分规范、工具和产品各自的版本。修改通用原则不自动改变产品版本，也不授权修改其他工程。知识库或其他外部位置只有实际同步后才能报告完成。

### 可复用的批次记录

| 内容 | 由当前项目填写 |
|---|---|
| 目标与身份 | 修改对象、版本、来源及基线 |
| 保留与变化 | 固定行为、允许变化、适用兼容要求 |
| 具体方案 | 实际职责、文件、接口及调用关系 |
| 变化性质 | 结构、修复、功能或优化 |
| 验证 | 条件、预期、实际结果、证据及未覆盖项 |
| 交付状态 | 已完成、剩余问题、放行条件和下一步 |

## 15. 说明性例子：只解释原则

以下均为假设场景，不是推荐架构、默认参数或验收清单。不同项目可以用不同实现满足同一原则。

| 原则 | 一个可能的应用 | 不能由此推导 |
|---|---|---|
| 按职责组织 | 某设备把数据采集与业务决策分开，以便分别验证 | 所有设备都必须建立同名文件，或采用相同任务数量 |
| 行为变化单独说明 | 某次目录整理同时调整启动等待，需要另列行为变化并验证 | 其他产品也应采用这一等待过程或具体时长 |
| 保持并发交接正确 | 某中断发布事件，处理方取走事件时要避免覆盖新到事件 | 所有事件都必须使用回调、全局标志或同一种临界区 |
| 吸收实现先核前提 | 某产品借鉴另一设备的接收缓冲方法，保留自己的协议与参数 | 来源工程的帧长、目录、驱动和参数也应一并复制 |
| 验证合并结果 | 两个分支分别改变数据生产与消费，合并后重新核对约定 | 两边单独测试通过就无需验证最终结果 |
| 配置按需求独立 | 用户明确要求某个附加模式单独调目标，因此分开对应配置 | 所有产品都应增加此模式、独立配置表或设置命令 |

# 嵌入式工程与代码重构原则

版本：v1.1；整理日期：2026-11-25。

适用对象：嵌入式固件的文件整理、工程调整、职责拆分、驱动移植、参考工程吸收及相关 BUG 修复。

形成依据：C300 项目的用户要求、后续整改方案及 2026-11-23 复审结论；本版补齐仓库 skill 分工与复用边界。[S1][S2]

## 1. 总目标与使用方法

**以安全和已确认需求为前提，保留需要保留的产品功能与参数，用尽量少的模块、明确的职责和可验证的接口完成重构，使工程更容易阅读、修改、验证和迁移 MCU。**

本规范适用于开发者、审核者及执行工程任务的 AI。主文是可复用原则；附录 A 是 C300 专属约束；附录 B 是上一轮问题的历史快照。复用到其他工程时，填写该工程自己的基线和约束，不能直接套用 C300 的功率、时序、平台、库或优先级。

使用步骤：

1. 在项目任务中填写第 2 节的范围表。
2. 将本文件放到项目现有 docs 目录，加入文档入口。
3. 将配套 AGENTS 简版合并到现有规则，保留原有有效要求；没有 AGENTS.md 时再新建。
4. 每批修改按“本批目标—具体变化—验证结果—剩余事项”记录，按已授权计划推进。
5. 更新工程后重新核实适用事实；历史审核结果不自动变成本次通过证据。

本规范不要求为每项小改动重新请求批准。对已明确、已授权的结构整理和缺陷修复，完成验证后继续推进；只有涉及尚未确定的产品行为、范围扩大或关键取舍时，才提出具体问题。

## 2. 开始修改前先固定范围

| 项目 | 必须明确的内容 |
|---|---|
| 当前目标工程 | 工程名、MCU、硬件版本、APP/BL 版本，以及本轮实际修改的目录 |
| 在役或对照基线 | 原始源码或提交号、构建依赖；重要交付保留哈希 |
| 参考工程 | 仅用于吸收的实现及其硬件、功率和软件前提 |
| 必须保留 | 充电功能、电池档案、参数单位、协议、存储兼容、生产部署行为等 |
| 已明确允许改变 | 用户指定的新需求、已确认 BUG 的修复及对应的预期行为 |
| 本轮目标 | 具体改哪些职责、接口或缺陷，达到什么结果 |
| 验证条件 | 可用编译器、完整工程、目标板、负载、客户端、升级工具及缺失项 |
| 交付范围 | 源码、工程文件、文档、测试记录、二进制和需要用户实测的项目 |

同时存在“原工程、参考 B 工程、当前修改版”时，要分别命名和保留身份。不能把参考工程当成产品基线，也不能拿上一轮源码的构建记录证明当前源码通过。

读取版本记录、todo 和计划后，还要核对实际文件。文档所说的“已完成”“未改变”必须与代码相符；冲突时记录冲突，不靠猜测补齐。

## 3. 将四类修改分别登记

| 修改类型 | 原则 | 验证重点 |
|---|---|---|
| 结构整理 | 移动、命名、拆分职责，保持可观察行为和既有调用约定 | 新旧函数映射、调用时机、编译链接、初始化和中断入口 |
| BUG 修复 | 根据实际问题修正行为，选择最小且安全的修改范围 | 触发条件、因果链、修复前反例、修复后回归及相邻路径 |
| 已批准的功能变化 | 明确需求对应的新行为，记录兼容性和部署影响 | 正常、边界、失败、恢复、旧配置及旧客户端 |
| 性能或空间优化 | 先确认瓶颈，再局部优化，不改变保护和参数语义 | 本版前后 map、耗时、栈、Flash/RAM 及功能结果 |

一个批次可以包含多类修改，但记录必须分开。改变启动、CBC、预充、Demo 或 OTA 行为时，不能只写“整理代码、功能未变”。

不为了保持所谓等价而保留已确认 BUG，也不以“顺手优化”为理由扩大功能变化。已做对的实现优先保留，避免整套重写。

## 4. 文件与工程整理原则

### 4.1 优先沿用现有目录

以下是职责放置建议，不要求把已有可工作的工程机械搬成新目录：

| 位置 | 内容与边界 |
|---|---|
| Application/app | 主循环和应用职责；可沿用 inc/src 或同目录 .c/.h |
| Application/driver | ADC、PWM、比较器、GPIO、串口、看门狗、时基等硬件实现 |
| Bootloader | 启动、镜像验证、升级恢复以及自己的必要驱动 |
| Shared | APP/BL 真正共有的数据格式、分区定义、CRC 等；不收纳杂散业务全局量 |
| 现有工程目录 | 工程文件、startup、链接配置、芯片 SDK、闭源库依赖与构建配置 |
| docs | 需求、架构、修改计划、参数、验证、版本和学习文档，提供一个总入口 |
| tasks/todo.md 或现有任务入口 | 维护一个权威进度表；其他位置链接到它，避免多份状态互相矛盾 |
| tests 或现有验证目录 | 主机检查、替身、必要脚本和证据；明确不加入目标固件 |
| build/artifacts 或现有产物目录 | 当前构建与发布产物；临时文件不混进正式源码目录 |

移动文件后同步工程引用、头文件路径、链接配置和脚本路径。统一文件名大小写，检查大小写敏感环境。保留供应商接口和 ABI 所要求的名字。

不要仅为风格统一大规模重命名可工作驱动、移动 SDK 或重建全部工程。清理历史资料时保留必要的基线、对照和回退信息，不删除仍有用途的原件。

### 4.2 模块数量保持克制

当前 C300 以六类业务职责为核心：sample、charge、protection、output、debug、mmi。LED、按键、配置、变量定义、启动和中断入口可以作为支持文件保留。

“六类职责”不是“整个工程只能有六个 C 文件”。但同样不应为每几个调用再增加一个 manager、service、coordinator 或纯转发包装。

新增模块应有明确的独立职责、状态归属和验证收益；如果在既有模块内即可清楚表达，就优先留在既有模块。

## 5. 应用层职责边界

下表适用于 C300 或已明确采用六任务结构的工程；其他工程按真实职责建立自己的映射，不强制凑齐六个模块，也不要求每一逻辑层单独建文件。

| 模块 | 应负责 | 不应承担 |
|---|---|---|
| main | 初始化、取得时间、任务节拍和顺序、系统级健康判断 | 大量充电分支、直接配置外设、完整协议分发、参数档案实现 |
| sample | 原码交接、零点校准、换算、滤波、极值、功率、采样快照、有效性与时刻 | 决定充电阶段、合功率继电器、直接恢复 PWM |
| charge | TC/CC/CV/FC、复充、充电限时、限功率、当前 MPPT 库调用、Demo 档案、候选输出及相关计量 | 直接操作硬件寄存器、绕过保护开功率、处理底层串口字节 |
| protection | 故障判定、锁止/恢复资格、供电和存储禁止条件、向输出提供许可 | 搜索 MPPT、业务协议收发、独立恢复功率输出 |
| output | 前台正常 PWM/功率继电器动作的统一审核与提交，首拍、斜率、预充和维护关断 | 决定电池化学参数、计算 MPPT、篡改其他模块的私有状态 |
| debug | 读取诊断快照、限量输出、统计和日志 | 改变正常控制语义、长时间阻塞控制、在快速 ISR 中打印 |
| mmi | 按键、面板/通信命令语义、配置请求、完整档案提交、显示和 OTA 交互 | 直接开 PWM、直接合功率继电器、重复实现充电和保护算法 |

职责表描述所有权，不强制每个功能都增加一层函数。模块内部函数能保持 static 就保持 static，对外只公开确有调用者需要的接口。

main 应一眼看清每项任务什么时候运行、使用什么数据、谁最后提交输出。初始化完成后，前台默认串行执行；不要仅因拆文件而引入 RTOS 或并行线程。

## 6. 应用与驱动的接口原则

### 6.1 两个方向分别处理

**硬件事件上行：驱动 ISR → 有界回调/事件/快照 → 前台应用消费。**

**控制命令下行：应用 → 明确的驱动接口 → 硬件执行与状态反馈。**

不要求所有普通函数调用都经过中断。中断负责真实异步事件；设置 PWM 候选、读取供电状态、请求复位等通过正常接口完成。

回调可采用已有工程的注册、弱符号或事件交接方式，选择简单、可验证的一种即可。回调必须说明执行上下文；在 ISR 内调用时，只允许对应上下文可承担的短操作。复杂业务仍在前台运行。

### 6.2 真实隔离 MCU 依赖

外设寄存器、SDK 类型、引脚、ADC 通道、定时器模式、比较器配置、Flash 操作、NVIC 和 CPU 临界区细节归驱动或既有板级配置。

应用使用逻辑通道、物理量和含义明确的返回值。公开头文件避免无必要地带出整套芯片头；驱动不依赖 charge、mmi 等应用业务结构。

改变 MCU 时，优先改驱动、板级映射、启动/链接及经过明确评审的库适配；业务状态机尽量保留。接口隔离不保证任意芯片都兼容原闭源库，还须确认处理器、编译器 ABI 和供应商支持。

## 7. MPPT 与参考工程吸收原则

### 7.1 当前 C300 保留原库

直接使用 HT32_Mppt_Solar.h 对应的既有库；应用中的计算调用及复位入口集中在 charge。不吸收 B/165W 的 MPPT 搜索算法，不再增加只做转发的两三层 MPPT 包装。

库的参数、单位、结构体布局、ABI、调用频率及内部状态语义必须有依据。不了解含义时，不通过写私有字段“修好”现象。

应用应区分“库计算出的候选”与“硬件实际输出”。加入首拍、斜率、CBC、预充或采样期限后，必须评估二者动态关系；库未更换不代表闭环行为天然等价。

以上是 C300 的具体选择。其他工程是否使用独立 MPPT 模块，应由该工程需求决定。

### 7.2 吸收 B 的每一项实现都要有理由

| 必须回答 | 内容 |
|---|---|
| 原问题是什么 | 当前工程的真实缺陷、复杂度或可维护性问题 |
| B 改善了什么 | 安全性、实际使用可靠性、逻辑清晰度或可验证性 |
| 前提是否一致 | 拓扑、器件、极性、MCU、采样、驱动和工作范围 |
| 保留什么 | 当前工程的功率、电流、电压、电池档案、协议和生产约束 |
| 怎样证明 | 修改前后对照、反例、必要目标构建及板测 |

参考其职责组织和已经验证的实现，不整包替换当前在役工程。参数、硬件假设和时序不能随代码一起无说明地带入。

## 8. 采样、共享状态与时间原则

### 8.1 采样必须可追溯

至少明确样本的来源、单位、序号、实际采样时刻、有效性和校准条件。只有新采样才能刷新新鲜度；重复消费旧快照不能把它重新标成新数据。

同一统计窗口内，电流、功率、极值和有效样本数应来自相容的数据。不能复采替换电流后继续使用原功率和极值，却仍宣称同一时刻数据。

换平台、重做校准、改变滤波条件时，要明确哪些历史窗口、候选和累计状态失效。校准放在 sample 所属实现中，由明确的启动或恢复流程调用；不能因分模块而在普通采样中反复校准。

### 8.2 共享状态有唯一所有者

列清每项关键状态的生产者、消费者、允许写入者与失效条件。跨 ISR/前台使用快照、短临界区、事件累积或代次等简单机制保证一致性。

volatile 不能替代读改写原子性、多字段一致性或事件不丢失设计。停机、故障、维护、换档之后，旧输出候选和旧合闸请求不能继续生效。

### 8.3 时间与次数分别定义

| 条件 | 应采用的依据 |
|---|---|
| 超时、冷却、充电时长、上报周期 | 单调时间或实际 elapsed_ms，并明确回绕范围 |
| 连续有效采样、滤波窗口、连续证据 | 新且有效的样本数量 |
| 容量/能量积分 | 有效功率及明确时间跨度，定义缺样处理策略 |
| 调试发送 | 带宽和时间预算；积压时不能补发大量旧数据阻塞控制 |

漏服务不补造 ADC 样本。也不能无限拿旧功率补算电量。涉及时间的变化应覆盖正常节拍、延迟服务、回绕和时间源停止。

### 8.4 喂狗应反映控制进展

运行期不能只因为主循环仍在转就持续喂狗。健康条件应观察关键生产者与控制流程在规定窗口内推进；不要求每一圈都产生全部新样本。

启动、校准、合法维护和 Flash 操作可有明确预算与专门策略，但不能成为无期限绕过健康检查的入口。不能用同一个已经停走的时间源同时证明自己仍然健康。

## 9. 中断执行与并发原则

1. 按保护实时性、控制截止时间和通信负载分配优先级。紧急电气关断通常高于控制采样，通信与慢业务不得侵占保护预算；具体数字由 MCU 和工程确定。
2. 不通过“所有中断设成同级”代替并发分析。必须列清可发生的嵌套、共享状态和最大关断延迟。
3. ISR 只处理必要的标志、数据搬运、快照、事件、计数及紧急关断。快速 ISR 不运行 MPPT、复杂业务状态机、Flash 写入或阻塞打印。
4. 允许经过预算验证的有界硬件等待；例如 ADC 等待必须有超时与安全失败路径，不能无限循环。
5. 串口可按实际需要进行有界组帧，但命令语义、配置持久化和升级业务在前台处理；完整帧发布后不得被下一半帧覆盖。
6. 临界区保存、恢复进入前状态，避免无条件开中断。范围尽量短，不能包住长计算、Flash 操作或整个业务流程。
7. 软件清除故障或恢复许可时重新核实硬件状态、事件和代次，避免刚发生的新故障被旧清除动作覆盖。
8. 关键快速链结合本版 map 核对向量、调用函数、常量及编译辅助函数；放入 SRAM 的单一入口不能替代整条链验证。

需要测量的至少包括关键 ISR 最坏耗时、关断延迟、采样超时、主循环最长服务间隔，以及通信或 Flash 负载下的表现。主机替身不能证明真实 NVIC、ADC 或模拟电流时序。

## 10. 输出、PWM、CBC 与预充原则

### 10.1 正常动作统一提交，紧急关断立即执行

前台正常 PWM 和功率继电器动作由 output 统一审核、通过驱动执行。charge 提交候选，protection 提供限制和许可，mmi 提交请求。

**硬件保护和驱动 ISR 可以立即关断，无需等待前台。** 不为“统一出口”而把紧急关断排队，也不在 ISR 中调用完整 output 状态机。该规则不限制 LED 等非功率 GPIO 的普通驱动。

重新启用必须由明确的恢复流程完成。恢复前核对当前故障、采样有效性、维护状态、候选代次和所需硬件条件；提交前后的复核按硬件与并发窗口设计。

### 10.2 PWM 行为写成可验收条件

明确极性、比较值与实际导通关系、关断值、预装载、死区、首次开波、停波和恢复过程。不能直接把 CCR/周期比当成所有输出引脚的导通比例。

首拍和斜率约束如果改变实际输出，单独登记行为变化，并测试候选与实际 CCR 的轨迹、限流/限压及闭环稳定性。

### 10.3 CBC 的统计和恢复语义必须完整

写清触发来源、硬件动作、软件计数、锁止条件、扣分条件及恢复资格。区分硬件逐周期行为与软件重新使能。

当前 C300 的 ISR 负责关断，前台凭新候选走完整恢复；不在 ISR 中修改库 Duty 或恢复 MOE。停波、首个恢复周期、连续故障和间歇故障都要有对应测试。

不能只验证“计数到阈值会停”，还要验证停止之后不会被旧事件、旧候选或同轮其他任务再次开启。

### 10.4 预充与继电器使用明确状态和新样本

为普通模式和 Demo 明确各自的合闸流程、等待、压差、单向资格、超时及失败动作。复用公共操作可以，不能无说明地混用资格条件。

涉及“停波后”“机械等待后”的判断必须使用满足时间关系的新样本。STOP、保护或维护进入时，尚未执行的合闸请求应能被撤销。

GPIO 锁存读回只表示命令引脚状态；没有触点传感器时，不宣称已确认机械触点。启动电压资格与物理吸合完成使用不同语义。

## 11. 电池档案与 Demo 原则

普通电池档案的功率、电流、电压、温补和保护参数按基线保留。参数必须带单位，并区分充电控制阈值、软件保护阈值、硬件比较器阈值和显示值。

每个支持的电压平台有自己的 Demo 档案。默认目标采用该工程明确选择的 CC→CV 电压，建立独立 Demo 目标配置；以后修改 Demo 时不牵动普通电池档案。

“独立目标”是数据职责，不要求新增应用模块。当前尚未确定的设置入口、面板命令和交互方式留待需求明确，不提前扩展协议。

修改 Demo 目标时，要核查控制上下窗、功率/电流限制、软件保护、硬件比较器及可工作范围，不能为达到目标而直接放宽保护。

模式和平台的选择、持久化、旧配置迁移、普通档切换与退出方式按已批准合同实现。默认值只是初值，不能覆盖用户有效的已保存配置。

## 12. 配置、Flash、通信与 OTA 原则

### 12.1 配置以完整有效版本提交

先校验请求，再形成完整候选配置，持久化并按策略校验成功后发布有效状态。失败不能出现新平台配旧阈值、新模式配旧限制等半套配置。

记录不存在与介质损坏分别处理。可选项缺失按需求使用默认值；有效旧配置可按既定策略继续使用，无法证明配置有效时按安全策略禁止功率。不得静默清空用户配置来掩盖写失败。

计量保存失败不提前推进已保存值、索引或清掉待保存状态。涉及冗余记录、搬页、CRC、序号和 commit 的变化必须覆盖失败注入与恢复。

### 12.2 APP/BL 共用格式与分区定义

真正共享的 Flash 地址、页大小、镜像范围和协议结构使用同一来源，必要时增加编译期校验。MCU、Flash 或链接布局改变后重新核对两个工程，不能只改一边。

### 12.3 通信既校验边界，也校验关系

校验长度上限、字段间长度关系、校验和/CRC、完整帧边界和生命周期。接收缓存、冻结帧和发送缓冲必须有容量与溢出策略。

命令生效、ACK 入队、硬件发送完成之间的顺序按协议定义；不能把 ACK 放进缓冲就当作对端已经收到。保护关断不能等待通信 ACK。

### 12.4 OTA 包含首装和失败恢复

准备、持久化状态、擦写、镜像校验、提交完成、发送结果和跳转要有明确顺序。持久化失败不能继续执行依赖其成功的破坏性步骤。

覆盖非对齐分片、断线续传、有界重试、校验失败、掉电恢复、同镜像重入和版本回退；不能无限递归恢复或在重连时无限重置预算。

新 BL 如果要求完成记录，工厂烧录和首装工具必须一同适配。DONE 的格式、CRC 和校验方式由本工程确定，不把 C300 的具体记录格式推广到所有 Bootloader。

APP OTA 不自动等于 BL 更新。列清新旧 APP/BL 组合、参数格式兼容与降级处理，交付和验证实际部署的组合。

## 13. 可读性、命名与资源优化原则

优先减少职责混杂、重复状态和重复分支，再考虑减少函数数量。简短代码如果隐藏调用副作用或安全前提，不算改善。

命名表达职责、状态和单位。保留 ABI、协议、持久格式及外部工具要求的名字；兼容适配集中且可追踪，不留长期混杂的两套入口。

关键函数说明：功能、执行上下文、输入单位、前置条件、状态/硬件副作用、失败返回和必要的时间要求。注释重点解释“为何必须这样做”，同时保持与实现一致。

只有配置改变才变化的参数，可评估在配置提交时预计算；依赖实时电压、电流、温度、模式、校准的数据，必须有明确失效和更新条件，不能缓存后忘记刷新。

资源优化使用当前版本前后 map 和测量。不能为了减少几行或几字节删除保护、超时、边界校验、故障恢复或有效诊断。

## 14. 分阶段执行与验证原则

| 阶段 | 工作 | 通过标准 |
|---|---|---|
| 0：建立基线 | 阅读工程、函数关系、参数、构建和现有结果 | 输入明确；本轮范围、保留项、行为变化和缺失证据可追踪 |
| 1：职责迁移 | 完成文件归属、接口和 main 编排 | 无漏编译/重复定义；函数映射和调用时机可核对；依赖方向清楚 |
| 2：有限修复 | 按事实修 BUG、实现已明确新需求 | 对应反例关闭；相邻路径回归；行为变化登记完整 |
| 3：当前目标构建 | 用本版源码和匹配依赖全量构建 | APP/BL 的编译、链接、地址、RAM/栈及关键链与本版产物对应 |
| 4：台架与部署 | 按改动验证功率时序、负载、Flash、协议和首装/升级 | 每项有预期、实际、条件、结果和证据，覆盖相应失败恢复 |
| 5：交付收口 | 同步源码、文档、版本、任务表及学习资料 | 文件可下载/解压；结论与实际验证一致；用户能据此继续验收 |

阶段可按风险合并或细分。已经获得授权且验证通过的工作继续执行，不要求每次停下来重新问一次许可。遇到确实依赖目标板或缺失输入的门槛，继续完成其他已授权可做的工作，清楚列出阻塞项。

测试应与改动风险相称：纯文档、机械命名和低影响整理不堆叠无意义测试；功率输出、中断、存储和升级逻辑的变化必须有对应验证。只验证实现自己的分支、却没有检查结果和失败后果的测试，不能代替有效回归。

## 15. 审核与结论表达原则

重要批次从职责与功能、功率与中断、采样与时间、存储通信与部署几个角度检查；同一问题由相关方向交叉核对。专家意见以证据收口，不按“多少人同意”判定。

每个问题写清：位置、当前事实、可达的触发条件、因果链、实际影响、复现方式、最小修改方向、验证标准及问题来源。区分继承问题、新引入问题、已批准变化、需求未完成和未验证风险。

严重性按实际后果、可达性和恢复成本判断：

| 等级/类别 | 使用原则 |
|---|---|
| P0 | 有证据支持的硬件损坏或人身风险路径；不能靠多重无依据假设推高等级 |
| P1 | 核心使用功能或关键数据完整性失效，例如特定正常部署下无法启动/恢复；按实际影响判定 |
| P2 | 部分功能、计量、计时或恢复缺口，影响使用但范围或后果较有限 |
| P3 | 维护、兼容、诊断、可读性等问题；如果在目标环境实际阻断交付，应重新按影响定级 |
| 证据缺口 | 缺少当前构建、波形或板测记录；列入验收待办，不自动称为代码 BUG |

验证结果分别标注：通过、失败、未执行、因条件缺失受阻、存在已知限制。主机检查、目标编译链接和实板结果分开列。

脚本退出 0 可能只是成功复现了一个问题；必须查看断言和结果含义。测试通过不应写成“绝对无 BUG”，应写明覆盖范围、剩余问题和放行条件。

## 16. 文档、版本与交付原则

版本分清 skill、规范文档和产品固件三种对象。纯技能或文档变化不修改产品固件版本；产品版本按其交付规则处理。

每个有实际变化的交付版本同步更新：修改说明、任务状态、接口/调用关系、参数表、验证记录和必要的学习文档。对本项目已有的 HTML、函数关系图、思维导图，变化影响到内容时同步更新；不相关页面无需重复制作。

版本号按项目既定策略递增或标注候选状态。源码、目标依赖、库哈希、map 与实际发布镜像对应；不能沿用旧日志代表当前结果。

如项目已指定知识库或 Obsidian 路径，按约定同步阶段摘要；未实际同步时明确记录，不写成已完成。

交付内容按本轮范围选择，涉及完整固件交付时至少覆盖：

- 可打开的源码与目标工程，必要依赖版本、构建说明。
- 改动清单、函数迁移表、已修问题和未关闭问题。
- 适用于本版的参数、状态、调度、中断和输出关系说明。
- 实际测试记录、复现步骤、未测项及用户实板验证表。
- 若发布镜像：对应 APP/BL、工厂/合并镜像、OTA 包、哈希及升级/回退步骤。
- 需要更新的学习 HTML/函数说明/关系图，以及清楚的文件入口。

不要混入旧固件、未使用 SDK、测试替身或临时产物，使用户误认为它们属于本版。交付压缩包应检查完整性，并确认关键路径和复现入口可用。

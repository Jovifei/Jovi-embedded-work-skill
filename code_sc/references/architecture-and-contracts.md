# 职责、接口与结构审计

在 Owner、文件组织、库边界、接口收窄、命名、布局或冗余审查时读取。以下检查以被审工程自己的已确认合同为准；它们不规定必须使用独立算法层或固定目录。

## 目录

1. 职责与依赖取证
2. 接口和副作用
3. 冗余与观测合同
4. 命名、结构体与 ABI
5. 配置和头文件

## 1. 职责与依赖取证

建立最小 Owner 表：`对象 | 当前 Owner | 允许 writer | producer/consumer | 清除/失效 | 上下文`。同一状态可以被多个模块读，同一事务也可分多步执行；要发现的是多个独立决策者争写或以不同规则解释同一事实。

- 充电阶段、会话、库算法、fault、采样、配置和输出资格分别追写点。名称为 `mppt_controller` 且含 charge stage 只是线索；先确认它是明确的 charge 编排 Owner、厂商固定结构还是被误当纯算法的双重 Owner。
- 如果独立纯算法已是本项目合同，其内部不应自行读取 charge/protection/driver 或拥有继电器/业务会话。若 charge 按项目约定集中阶段、库调用及复位，这种同模块组织合法；区分逻辑责任即可。
- 业务 Owner 表达停机、会话失效、模式/约束；计算 Owner 解释积分/搜索内部动作。直接改私有积分器、猜写库字段或由高低层互读内部状态时，给具体路径和后果。
- 查 lifecycle：同一 STOP 在外层、transition、wrapper 分别决定 reset，不能以幂等免审；同一 Owner 的有界重试或两个不同时间屏障不自动是重复生命周期。
- 配置、新模式或同一规则改动若必须散落多处，列出规则 Owner、真实消费者与已发生/可达的分叉。不要仅以文件数判断 shotgun surgery。

同时查 include、call、write 和 callback 图，必要时用 SCC 辅助。重点追 `driver -> app 私有状态`、`sample -> charge/output` 为日志取状态、业务引用 debug 私有字段、同层互改状态。通过驱动定义的中立事件回调上行不等于非法反向依赖；应记录 ISR/前台上下文、数据生命周期及回调工作量。

对 PWM/MOE/CCR、功率继电器 GPIO、fault latch/clear、stage/session、库 init/reset、epoch/pending 列所有宏、函数、ISR 和 callback 写点。正常输出经执行 Owner，驱动 ISR 紧急关断是设计中的独立安全路径；不把它当作普通输出 Owner 冲突。LED 等普通 GPIO 另按其职责审查。

## 2. 接口和副作用

记录核心函数的 `Inputs / Hidden Inputs / Outputs / State Mutation / HW Side Effects / Caller / Timing`，核对声明、实现、注释与调用者是否一致。

| 线索 | 必须补查的合同 |
|---|---|
| 接口收整个 sample/profile/protection/charge ctx | 实际消费字段、只读性、完整快照一致性、私有状态泄漏、ABI；不是按参数大小自动判错 |
| 已传 snapshot，内部又读 latest/硬件 | 是混代决策还是有意的提交瞬时复核；在明确执行位置记录复核和失效规则 |
| 无参 helper 读 file-static 状态 | 是否是本 Owner 的私有实现，还是伪装成纯函数或跨 Owner 隐藏输入 |
| getter/preview | 是否写状态、推进积分、改变滤波，或通过共享指针修改正式对象 |
| `try_start/enable/commit` 返回 true | 合同是转移完成、请求接受还是目标已满足；检查 caller 如何使用，缺合同先补证据 |
| 参数 0 / duty / relay_closed | 是否混淆有效零、停机、未启用、无效、候选、硬件设定或物理反馈 |

跨 Owner 优先传必要标量或窄 DTO；已有完整一致快照、稳定 ABI 或统一测量合同可保留。DTO 不应把每个内部状态都复制成新的真值；不为一个字段机械新增 `.h/.c`。

控制输出按证据区分：

| 语义 | 含义 |
|---|---|
| candidate | 计算/策略提出的候选 |
| approved | 当前策略与安全条件允许的值 |
| committed | 执行 Owner 接受/提交的命令或回执 |
| driver_setting | 驱动保存或寄存器已写的设定 |
| physically_effective | 已发生的波形/执行状态，需要硬件时序或实测依据 |

某工程可以合并批准与提交、提交与驱动写入；如实描述，不要求新增五套字段。继电器 ODR/IDR 不自动等于触点闭合；只有与硬件反馈能力相符才声明 contact state。

## 3. 冗余与观测合同

先建矩阵：`候选 | 语义/单位 | Owner/消费者 | 输入身份/时点/有效性 | 运算/副作用 | 保留/合并/待证`。数值当前相同不足以合并测量与限幅值、即时值与历史、业务上限与独立硬件绝对上限。

- 追生产方、控制/保护/存储/协议消费、授权遥测、测试及内部反馈。积分、seq 去重、回算、过滤、缓存、故障代次和事务记忆都是实际消费者。
- 只有测试读取的公开镜像可建议收窄/删除，并迁移到真实内部或行为断言；不要为旧夹具恢复生产镜像。
- fault/action/enum 只有定义或消费而无 producer 时，核实是遗漏、保留 ABI、未来需求还是不可达代码；报告功能缺失需要真实需求与调用路径。
- 授权遥测及诊断不是因名字含 diag 就可删。对路测减包列观察目的、字段来源、两种模式等已定合同、单位、编解码、默认开关、带宽和发送预算。
- 诊断/shadow 对照进入批准、候选发布、inhibit 或恢复决策时，查是否有已批准的产品目的；迁移验证可在 Host 双算，不能悄悄增加生产 veto。
- 空 wrapper 可合并，但保留实际 ABI、IRQ 桥、集中写点、恢复握手及清楚的语义边界。恒 true 的 prepare 只有在查完返回与 caller、且不需失败语义后才可改 void。
- 准备写零不等于零已生效；自然更新、首脉冲、写前/写后和恢复中断后的保护是不同屏障，不按短函数或相同值去重。

同一业务功率/电流/电压规则应有单一来源。独立绝对保护可保留，但需要不同职责、来源及名称。原厂库内部阈值/参数可能受 ABI 或算法合同约束：先核实单位、可配置入口及复用方式，不要求编辑不可改库或猜写私有状态。

## 4. 命名、结构体与 ABI

遵守项目自有 app_/drv_ 命名约定，通常为 snake_case；保留 SDK/CMSIS、startup IRQ、回调、协议、持久格式、汇编及闭源库约定名。

改名建议提供 `旧名 -> 新名 -> Owner -> 声明/定义/所有调用/回调/工程/测试/decoder/docs` 映射。搜索结果分为活动旧名、兼容入口、SDK 和历史基线，不以清零所有旧字符串为目标。校验文件名与 include 大小写、实际构建路径。

对可调整的内部结构，按项目约定把相同声明类型集中，保持同类原相对/用途顺序；float、uint32_t、int32_t、uint16_t、uint8_t、bool 分别处理，bool 与 uint8_t 不因同宽混组。组序优先项目约定，否则结合目标自然对齐选择。

重排前追位置式/指定式初始化、offsetof/sizeof、raw memcpy/序列化、Flash/协议/DMA/寄存器、packed/bitfield、汇编、回调与闭源库布局。固定布局保留并记录例外，不因私有命名就假定没有外部合同。此规则不要求新嵌套 struct、改函数形参或重排厂商结构。没有目标 sizeof/map 不承诺固定 RAM 收益。

关键注释说明功能、执行上下文、输入单位、前提、状态/硬件副作用、失败返回及时间要求。注释错误与行为错误分开；名称相似或某个后缀本身不证明越权。

## 5. 配置和头文件

按 Product/Safety、Charge、库调参、Driver/HW、Debug 等责任找唯一来源，不让 main.h 成为杂散全局桶。归属可通过现有文件、私有 static 或最小公共合同表达；不自动要求再拆 `algorithm_config.h` 或增加转发头。

公共头只暴露真实消费者需要的类型。独立头的合理理由包括稳定 ABI、独立 Owner、多消费者或解除依赖环；少文件不是唯一目标。优先直接包含符号所属合同，禁止偶然传递 include 成为无法说明的安全依赖。

对安全 `#if` 追实际 translation unit 的定义来源和预处理值、工程 define、同名覆盖及运行分支。直接 include 缺失但稳定公开头/构建定义明确时可成立；只有不可靠依赖是维护问题，保护被实际关闭并可达时才据后果升级。默认保留必要显式检查，用户明确移除的 `#error` 不用其他编译失败手法恢复。

# 证据、合并与报告

在全面复核、外部审核核验、跨版本/合并验收、构建验证或出具审查报告时读取。先固定被审内容，再判断具体事实；结论与严重度不能由测试数量、审核人数或架构名称代替。矩阵中的对象类别用于查关系，不预设工程有这些模块、字段或文件；具体对象由当前输入提供。

## 目录

1. 来源与变更登记
2. 集成合同与验证
3. 结论类别和严重度
4. 完成门与报告模板

## 1. 来源与变更登记

| 身份 | 最少记录 |
|---|---|
| 原工程/在役基线 | repo/路径、ref/SHA 或 hash、目标/硬件、库和构建依赖、保留合同 |
| 参考工程 | 独立身份、吸收目的、拓扑/极性/工作范围等前提，不能代替产品基线 |
| 当前修改版 | 实际工作树内容、当前目标/defines/include/库 hash、APP/BL 与产物 |
| 验证对象 | 对应的实际源码身份、命令/工具/条件、目标、时间和结果 |

只有代码片段时写范围；只有旧远端时不能验收未提供的本地修复。测试后继续修改内容，要判断结果是否仍覆盖最终内容；必要复跑只围绕新差异/既有门禁，不无目的重复全部测试。

逐项核验版本记录、todo 与真实代码。区分继承问题、本批引入、已批准变化、需求未完成和证据不足；引用历史审核只作为待核事实。外部报告每项追本版位置、调用者、可达分支与对照，不按意见人数投票。

改动登记用 `文件/函数 | 旧职责/行为 | 新职责/行为 | 结构/BUG/功能/优化 | 依据 | 验证`。一个批次可含四类；改变库调用频率、首拍、恢复、采样期限或部署不能只标结构未变。

参考工程吸收逐项回答原问题、改善点、前提一致性、保留参数/协议、前后证据。参数、硬件假设和时序不得随实现无说明迁入。

## 2. 集成合同与验证

Merge/rebase/conflict resolution 形成新审查内容。父分支的 PASS 不传给合并结果，检查以下适用矩阵：

| 合同 | Producer/Owner | Consumer/验证 |
|---|---|---|
| API/typedef | 当前声明、定义及类型归属 | 所有目标 caller/callback、旧 public 与新 private 是否并存冲突 |
| 状态/命令编码 | 编码、产生、清除及兼容来源 | 策略、协议、测试和恢复路径一致 |
| 动作禁止条件 | 产生、清除及有效期 | 当前工程的启动、执行、恢复和维护入口 |
| 异步入口 | 事件源、中断路由及入口绑定 | 当前链接实现、事件交接和实际消费者 |
| build membership | Keil/CMake/Make/linker/CI | 正确文件、大小写、include、define、APP/BL、SDK/库 |
| tests/docs/tools | 当前合同与复现路径 | 测试未失效/skipped，decoder、烧录/首装/升级工具与文档匹配 |

查删去的 public header、typedef/API/fault bit 是否被恢复，以及是否有实际旧消费者或兼容合同。旧名残留可以是 ABI、SDK 或历史资料；不把每个命中都当回归，也不允许旧源文件被幽灵编译或两个真值同时生效。

安全宏看实际 translation unit 的预处理结果：唯一来源、直接/稳定公开 include、project define、覆盖关系与可达条件。缺直接 include 不能固定 P1；宏未定义导致保护关闭后，要继续查受影响动作和后果。用户已明确删除的编译禁令不可换壳恢复，但仍需验证实际值和运行安全门。

IRQ 使用当前 startup/map/源文件及外设开启条件。没有强 C 函数可能由汇编/别名提供；只有 weak 声明不能证挂死，真实落入不可用的默认处理且中断可达，才确认相应故障链。

选择与风险相称的验证：

- 用 `rg`、调用/写点搜索及必要图分析核实 Owner、直接合同、旧符号和编译成员；图不是源码证据替身。
- 使用项目现有严格编译/静态分析/Host 测试，能运行适用目标构建时执行；工具/依赖缺失写受阻。无必要不新建脚本、模拟所有硬件或给纯文档堆测试。
- 功率、并发、存储、协议和升级修复需要修复前反例、结果断言及相关失败/恢复回归。测试只复述实现分支不足以证明输出与后果正确。
- 检查脚本实际跑了什么、断言与预期、日志含义和退出码。退出 0 可能表示成功复现缺陷；failed/skipped/not run 要分别记录。
- 性能/Flash/RAM 收益使用当前前后目标 map、相同工具链/选项和测量；源码行数、Host 对象大小或旧记录不能替代。
- 等价重构使用指定基线与当前版的同输入轨迹，覆盖变更状态、时序、限制来源和异常分支；已批准的行为差异明确排除并另验收。

## 3. 结论类别和严重度

先分类，再按可达的实际影响定级：

| 类别 | 需要的证据 |
|---|---|
| 可确认 BUG | 当前源码因果链或可复现失败，满足相应触发/合同条件 |
| 结构问题 | 明确 Owner/边界/重复解释/依赖等证据，可尚未发生板级故障 |
| 需补证据 | 缺源码、调用链、协议、宏实际值、当前构建或产品合同 |
| 需板级证据 | 真实 MCU/模拟时序、极性、保护延迟、触点、负载或掉电等才能确认 |

P0 要有可达硬件损坏/人身风险链；P1 为核心功能或关键数据完整性失效；P2 为局部功能/计量/计时/恢复等具体影响；P3 为维护/兼容/诊断/可读性问题。结构问题单列，不一律降为“风格”，也不因为叫 Owner inversion 或 mixed snapshot 就固定 P1。维护问题若实际阻断交付，按真实后果重评。

来源和证据可分开：例如“本批引入的结构问题、源码证实、未板测”，不必把所有待板测事项叫 BUG。证据缺口列验收待办，无确定因果链时不能拼多层假设抬成 P0。

| 证据标记 | 证明范围 |
|---|---|
| SOURCE_CONFIRMED | 所见当前源码的静态事实/可达关系 |
| HOST_PASS | 实际执行的 Host 输入/替身/断言；不证明真实中断/波形 |
| STATIC_ANALYZER_PASS | 指定规则和目标条件下的分析结果 |
| TARGET_BUILD_PASS / KEIL_BUILD_PASS | 当前目标编译/链接、配置/成员/ABI等可检查项 |
| BOARD_PASS | 指定板卡、仪器、固件、负载/场景下实际通过的结果 |

每项另外标通过 / 失败 / 未执行 / 因条件缺失受阻 / 已知限制。Host 与目标构建均不等于 BOARD_PASS，板测一个场景也不是无限制认证。

## 4. 完成门与报告模板

局部审查沿必要链取证，并明确没有覆盖的域；整改限于已授权范围。全面审查按适用性核对：

- 状态/决策/lifecycle Owner、include/call/write/callback 及逆向依赖。
- 正常功率写点、紧急关断、首拍/末拍/恢复时间线、ISR guards/TOCTOU。
- snapshot 代次、校准/功率同源、真实时间/样本数、缓存/模式/preview 副作用。
- fault/action/veto 的产生、消费、清除及恢复；产品限制单一来源与 ABI 例外。
- WDT 进展、ISR/控制 deadline 与通信/Flash 负载预算。
- 配置/计量事务、协议字段关系、APP/BL 共享合同及实际首装/升级组合。
- 当前目标构建、合并合同、适用测试、文档与交付入口。

不适用项说明理由。无法确认的必要项注明验证不完整并给缺口，可使用项目现有状态标记；无需为了填表制造新模块/新测试。发现实证高风险先报告，继续完成其余可做工作。

最小问题记录：

```text
ID / 来源 / 结论类别 / 严重度：
当前内容身份与位置：
合同与源码事实：
可达触发 -> 因果链 -> 实际影响：
反例/证据层级、尚未验证条件：
最小修复方向、验证标准：
```

最终先讲主要结论，再放问题表、必要 Owner/时序/事务关系、验证表和收口状态。修复后的 headers/API/project membership/tests/docs/deployment 对应同一内容；历史日志不得移作本版成功证据。已授修复/后续阶段授权继续生效，不默认每个门后暂停求许可；产品行为未定或真实阻塞才提出具体缺口。

# 配置、通信与部署

在配置/档案提交、Flash 维护、UART、APP/BL 分区、OTA 和首装验收时读取。格式、顺序和允许回退按本工程合同判断；这里列的是审查关系，不规定所有产品使用相同 CRC、DONE 或事务实现。

## 1. 完整配置版本

追踪请求校验、完整候选构造、运行许可、持久化、读回/CRC 校验、有效版本发布和结果返回。常见合同是在持久化成功后发布；已有原子运行切换与失败回滚合同也应按其真实语义审查，不能只因顺序不同自动判错。

需要回答：

- 平台、模式、目标、阈值、功率/电流限制与校准条件是否属于同一有效版本。
- 提交期间哪些任务还能读旧版，何时整体看到新版；是否会新平台配旧阈值。
- 保存失败时是否维持有效旧版或按安全策略禁止功率，是否给真实失败结果。
- “记录不存在”“旧格式可迁移”“数据损坏”“写/校验失败”是否区分。
- 可选配置缺失是否按需求取默认值；默认值不能覆盖有效用户配置，不能静默清空来掩盖失败。
- 配置改变是否撤销旧输出/合闸候选、重建受影响统计/缓存及必要硬件条件。

普通电池档案和 Demo 独立目标的关系按产品需求。独立数据职责不自动需要新模块/新协议；控制上下窗、功率/电流限值、温补、软件保护、硬件比较器和可工作范围须相容。不能为达到 Demo 目标擅自放宽保护。

## 2. Flash 事务与维护

对 CRC、序号、双副本、commit、搬页/擦写列 `准备 -> 写入 -> 校验 -> 发布/索引推进 -> 清理旧记录` 的实际路径。掉电/失败后必须存在明确可恢复状态；不要因函数返回 0 就假定记录有效。

计量保存失败不得提前推进已保存值、记录索引或清除 dirty。重试须有界，不能无限递归、无限消耗擦写寿命或用无提示恢复默认值掩盖错误。

维护不止是 Flash driver 检查 PWM=0。核查进入 veto、正常输出撤销、必要采样暂停/失效、ISR/Flash stall、WDT 策略、失败状态和退出资格。恢复时使用匹配配置代次的新样本/新候选，不能刚取消 busy 就直接旧大 Duty 或旧合闸请求重启。

运行期写 Flash 若允许功率继续，要求硬件与实时预算依据；若项目要求维护停机，按该约束检查每个入口，不能自行把两种策略替换。

## 3. UART 边界、字段关系和完整帧

列接收环/组帧缓冲、冻结帧、消息对象、发送队列的容量、Owner、发布/释放及溢出策略。ISR 可在预算内组帧，命令语义、参数持久化和升级业务在前台处理。

逐层同时检查：

1. 外层声明长度、实际接收长度、头部/尾部、CRC 覆盖范围与最小帧要求。
2. 内层 payload/block 长度、offset、镜像总长、剩余空间及彼此关系。
3. 加法/减法溢出、负值/符号转换、单位和对齐；先检边界再做索引/拷贝。
4. APP 与 BL 对同一帧/记录是否使用相同长度规则，不能一边校验外长一边信任内长。
5. 冻结完整帧到前台消费期间，下一半帧是否覆盖；重连、拆包、合包、重复帧和超时是否有明确状态。

例如 `declared_payload <= max` 与 `received_frame <= capacity` 都成立，仍不能证明 `header + declared_payload + trailer == received_frame` 或分片关系正确。具体等式按协议定义，不凭示例改协议。

本地板卡执行范围与协议合法编码可以不同。新增拒收、限幅或停机必须有合同依据；不因本板上限就无授权拒绝协议允许的转发/显示值。

命令生效、ACK 入队、DMA/串口发送完成与对端确认是不同事件。按协议确定跳转/复位前等待哪个条件及有界失败路径；保护 hard-trip 不得等待 ACK。

## 4. APP/BL 共用与升级事务

核查真正共用的 Flash 地址、页大小、分区、镜像范围、记录布局、CRC 与协议常量是否同源。公共定义可以配编译期断言；MCU/Flash/链接布局改变必须同时检查 APP、BL、烧录/打包工具和实际镜像，不能只改头文件一边。

列出升级状态机的实际顺序与失败分支：准备/安全停机、持久化升级状态、擦写、镜像校验、完成提交、结果发送、跳转。依赖持久化成功的破坏性步骤不能在失败后继续。

按变化覆盖非对齐分片、短/超长/关系不符的帧、重复/丢失分片、断线续传、有界重试、CRC/镜像失败、掉电恢复、同镜像重入与回退。重连不能无限重置总预算；成功复现一条失败不等于功能测试通过。

对跳转资格核查向量/栈/入口、地址范围、镜像校验、相关中断/DMA/外设状态及看门狗合同。缺芯片或当前链接资料时给证据缺口，不臆造通用跳转序列。

## 5. 首装、兼容和交付

新 BL 要求完成记录或整镜校验时，检查首次工厂烧录是否生成合法元数据，烧录地址/顺序/CRC 是否匹配，新 BL 能否冷启动工厂 APP。不能只验证 OTA 路径生成记录就宣布量产可用。

列兼容矩阵：`实际部署 BL | APP | 参数/记录格式 | 冷启动 | OTA | 回退 | 配套工具/证据`。APP OTA 不自动替换 BL；分别验证新旧组合和不支持组合的明确失败方式。

发布范围包含新 BL 时，核对工厂/合并镜像、OTA 包、烧录/升级工具、依赖版本、配置迁移及回退步骤。格式和 DONE 校验由该工程决定，不把某次 C300 的实现数值推广为统一 Bootloader 标准。

验证记录区分源码/Host、当前目标编译链接、擦写/掉电/负载实板、首装工具实际流程。没有首装证据列部署待办；源码已经证明正常工厂流程缺记录而无法启动时，才按实际影响给功能缺陷等级。

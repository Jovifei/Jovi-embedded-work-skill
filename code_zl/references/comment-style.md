# Jovi 注释样式与模板

仅在本次授权范围内采用项目已选择的样式；下文展示 Jovi 样式，项目已有其他有效样式时保留。通用要求是说明真实合同、减少重复并保持代码语义。示例里的函数、字段、目录、数值和行为只解释这些要求，不要求目标工程存在同名对象，也不成为命名、模块划分或参数的验收条件。

## 1. 函数头与声明

### 唯一合同头（Jovi 样式示例）

```c
/*---------------------------------------------------------------------------
 Name        : static bool elapsed_at_least(uint32_t now_ms, uint32_t start_ms, uint32_t wait_ms)
 Input       : now_ms - 当前单调时刻（ms）
               start_ms - 起始时刻（ms），与 now_ms 来自同一时间源
               wait_ms - 所需等待时长（ms）
 Output      : true=已等待足够时长；false=还未到期
 Description : 用无符号时间差判断是否到期，不修改状态，也不等待。
               调用方须保证实际间隔未跨过时间源的一整圈，且 wait_ms 在项目允许范围内。
---------------------------------------------------------------------------*/
static bool elapsed_at_least(uint32_t now_ms, uint32_t start_ms, uint32_t wait_ms)
{
    return (uint32_t)(now_ms - start_ms) >= wait_ms;
}
```

这是格式示例；这种名字清楚的简单私有 helper 在真实任务中可以省略合同头。复杂编排、安全副作用及硬件时序入口不能因为函数短就省略必要合同。

| 字段 | 写法 |
|---|---|
| `Name` | 逐项对照实际签名：限定词、返回类型、函数名、完整形参；长签名可对齐续行，不能用省略号代替参数 |
| `Input` | 一个参数一项；无形参写「无」，必要的隐含状态前提在 Description 说明 |
| `Output` | 返回值、错误码及其含义；`void` 可写「无返回值」，通过指针返回的内容必须说明 |
| `Description` | 当前函数的目的、执行上下文、状态/硬件副作用、调用前提、阻塞/时间边界和失败/恢复动作 |

多布尔参数不能合成一句「标志」。例如 `sample_valid` 是输入事实、`recover_allowed` 是恢复资格、`stop_requested` 是停止命令；先核实源码，再分别说明 true/false 如何改变本函数去向。

函数头只描述紧挨着的函数。发现 Header A、Header B 一起贴在函数 B 上时，查签名和函数体后移正 A，不留下两个合同头。不要把「调用方先读回执、再计算、再调用本函数」写成本函数步骤。

### 头文件声明

采用本样式时，头文件使用行尾合同摘要，不复制 `.c` 的整段函数头。以下接口仅演示说明方式，不要求新增或改名为这些接口：

```c
bool sample_snapshot_read(sample_t *out); // 取得最近一次完整快照；false 表示尚无有效数据
void output_stop_request(void);          // 请求前台停止正常输出；是否立即停波由实际实现合同说明
```

示例摘要须由实际实现确认。详细字段含义归定义处，声明只保留调用者需要的前提与结果。不要让读者从一句「设置状态」猜出失败是否保留旧状态。

## 2. 白话用语与重复说明

### 先说动作，再放标识符

下表是不同语义的说明例子，不是项目必须采用的字段、状态或寄存器清单；术语在本项目有其他约定时，以已核实的定义和消费者为准。

| 术语 | 按事实采用的中文 |
|---|---|
| candidate | 本次计算的候选值，还没有经过最终输出许可 |
| approved | 当前检查后允许的值，仍不等于已经输出 |
| committed | 已提交给执行层的命令；若有回执，写清回执能证明什么 |
| driver setting | 已写入驱动的设定值，是否经过定时器更新要另查 |
| physically effective | 有对应硬件事件或测量证据的实际输出状态，注明证据范围 |
| Arm / re-arm | 请求或允许重新打开输出；具体动作由本函数实现决定 |
| Disarm | 取消输出许可或关闭输出；是否同时关闭比较器必须核对实现 |
| MOE | PWM 主输出使能位；置位后是否发波还受计数器、通道、Break 等条件影响 |
| pending | 已留下、等待某个消费者处理的事件或请求 |
| active | 当前检测条件仍成立的故障，按该字段实际定义说明 |
| latched | 保留的故障证据；条件消失后如何清除按代码说明 |
| dirty | RAM 中有尚未按规定完成保存的修改 |
| snapshot | 一次交接取得的一组数据；采样时刻、有效性和是否同窗看生产规则 |
| 传能资格 | 软件判断的许可；除非有测量证据，不说已确认真实电流/功率 |
| 功率上限 | 当前允许请求的最大功率，注明实际约束对象及单位 |
| 保持模式 | 写出该模式实际降低什么、保留什么，不用俗称代替状态条件 |
| MPPT reset | 写明清除的算法状态，区分单片机复位与候选/历史窗口失效 |
| Fail-Closed | 条件不能确认时不放行；同时说明代码实际怎样处理 |

不要机械替换成同一长句。例如 `pending` 可能是发送请求、故障事件或配置写入请求，必须查真实生产者和消费者。

### 一处事实有一个说明位置

```c
typedef struct
{
    uint32_t captured_ms; // 实际采样时刻（ms），由采样生产者填写
    uint16_t voltage_mv; // 电压（mV），无效时不得用于控制判断
    bool valid;          // 本次采样已满足校准和有效性条件
} sample_t;
```

消费点写「为什么本处要判断」，不再把三个字段含义逐行复述：

```c
if (!sample->valid)
{
    return false; // 本次没有可用于控制的采样，保留上层对失败的处理机会
}
```

这段本身没有关 PWM，不能注释成「无效采样时立即停波」。若调用方收到 false 后关断，可以在调用点说明该动作。

相邻两个独立安全检查若针对不同时间点，应保留各自原因。例如提交前复核故障、提交后识别新中断，不能因都提到「故障」就删成一条。

## 3. 控制流与 Init

### `.c` 的基本分工

| 内容 | 样式 |
|---|---|
| 文件头、函数合同、大段必要说明 | 多行 `/* ... */` |
| 功能分节 | 短 `/* 静态变量 */`、`/* 板级初始化 */`，不用等号装饰 |
| 判断、失败后果、短说明 | `//`，放相关代码上方或行尾 |
| 普通自明赋值 | 默认不逐行复述；明确逐行任务按用户粒度解释用途 |

不要添加重复函数名的小标题；`Name` 已承担签名识别。采用 `//` 前确认不会吞掉同一行后续代码或多行宏内容。

### 分支与返回

```c
if (next == s_rx_tail)
{
    s_overflow = true; // 本例记下丢字节事实；读写指针与恢复由现有接收流程处理
    return;
}

s_rx_buf[s_rx_head] = ch;
s_rx_head = next;
```

例子只演示如何解释满缓冲后果，不证明该共享方式已满足目标 MCU 的并发要求。`volatile` 不能作为多字段一致性的注释依据。

```c
switch (state)
{
case RX_IDLE:
    break; // 当前没有完整帧，保留接收状态等待后续字节

case RX_READY:
    consume_frame(); // 本例消费者同步处理已冻结的完整帧
    break;

default:
    reset_receiver(); // 本例把未知状态退回接收初态，不保留残帧
    break;
}
```

这里的每个动作都要和真实代码对应。用户没有要求逐行时，不强制给所有自明 `case` 再写一遍枚举定义。

### 初始化按实际阶段说明

函数头先说本次初始化的能力和上下文，函数内采用类似分节：

```c
/* 外设时钟 */
/* GPIO：按本板复用与安全初值配置 */
/* 定时器：时基、通道与预装载 */
/* 保护：输入来源、极性与解除后的恢复方式 */
```

不要把示例板的引脚、载波频率、互补方式或自动恢复写到其他工程。非显然行说明寄存器动作的实际后果，例如「该位只允许硬件恢复，软件锁止资格在另一入口维护」；是否成立必须核实手册与当前代码。

连续 DDL 字段已有明确分节时少加重复注释。纯等待循环可以一条说明等待条件和现有超时/失败路径；源码没有超时时明确该事实并报告风险，不能凭注释增加超时。用户明确要求每行解释寄存器配置时按该粒度处理。

## 4. 头文件、字段与宏

采用 Jovi `.h` 样式时，分节标题下一行就是声明，不空一行；分节之间保留一行空行。字段、枚举、宏和 API 的行尾中文按块对齐。

```c
//=================== 接收状态 ==================================================
typedef enum
{
    RX_IDLE = 0,  // 当前没有可消费的完整帧
    RX_READY = 1, // 已发布完整帧，等待消费者取走
    RX_ERROR = 2, // 接收失败，等待现有恢复入口处理
} rx_state_t;

//=================== 接收接口 ==================================================
bool rx_frame_read(uint8_t *out, size_t capacity, size_t *length); // 拷贝完整帧；失败原因与缓冲所有权见实现合同
void rx_reset(void);                                             // 清除本例接收上下文及残帧
```

结构体内可用 `/* 分组标题 */`，但不得为注释分组改变布局。只有项目要求同声明类型集中时才按该样式检查并报告；已有语义分组不因此被判不合格。协议、Flash、DMA、packed、bitfield、寄存器和 ABI 布局保持其约束；按声明类型检查时不能因位宽相同就混成一类。

```c
#define FRAME_MAX_BYTES 256U  // 本例接收缓冲容量（字节），含头部与校验字段
#define QUERY_PERIOD_MS 1000U // 本例请求周期（ms），具体服务延迟由调度决定
```

协议字段写清单位、比例、范围、每个 bit 的含义及实际依据。错误码分别写出真实原因；不同原因目前共用错误码时如实说明，不能在纯注释任务中改返回值。废弃字段仅在确已废弃时标记，并注明实际替代项。

## 5. 文件头、日志与协议出处

文件头按本次需要说明模块职责、调用上下文、关键单位/约束与资料出处。保留版权、许可证和供应商要求；用户仅要求局部函数时，不统一全仓 Doxygen 或文件头。

日志字符串属于可观察行为；纯注释不改标签、格式或字段。需要说明物理链路和模块时引用项目实际标签，如 `[BUS]`、`[MQTT]`，不要把其他项目标签表硬套过来。

协议出处应能定位到实际资料路径、版本、章节或表格；不存在时不虚构文件。读取乱码资料时先判断编码，可使用已有运行环境的 GBK/GB18030 解码能力；不要把乱码猜成单位或枚举值，也不为注释任务新建转换脚本。

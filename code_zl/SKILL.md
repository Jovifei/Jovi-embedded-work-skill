# Code_ZL 代码注释整理技能

**Version: V0.2.12**

用中文短句说明当前代码的真实合同，让读者看清「做什么、为什么、在什么条件下成立」。保留 `code_zl` 兼容名称。读取本项目指定的规范入口，优先遵循已采用的注释样式；项目采用 Jovi 样式时使用本技能模板。

本技能规定说明内容、真实性和修改边界，不规定产品的函数名、文件名、模块数量、任务组织或参数。资源中的具体标识符、目录、代码和数值都是说明原则的例子；只有本次需求或当前项目合同明确采用时，才成为该项目要求。不得为了匹配例子新增接口、迁移职责或修改实现。

## 1. 先固定本次范围

1. 读取目标文件完整内容、调用者、相关定义，以及项目已有规范、批准合同和验证记录。区分目标工程、产品基线、参考工程和当前修改版；参考实现与历史报告不能代替当前事实。
2. 锁定用户指定的版本、文件、改动行和粒度。只补注释时保持 C token、预处理指令、宏续行和条件编译语义不变。用户只要一个函数时，不扩展成全文件或全仓改头。
3. 已授权格式或布局整理时才使用第 6 节的等价门。改名、成员重排、API/宏删除、职责迁移、状态机或时序修改按 `code_wrt` 流程单独处理；未授权时记录问题并继续可完成的注释，不偷偷修逻辑。
4. 分清注释修正、等价格式/布局、已确认 BUG 和已批准行为变化。注释揭示了 BUG，不代表已经修复；源码已被另一个获授权任务修正时，注释必须跟随实际新版。
5. Git 核对默认只读。暂存、提交、推送等写操作只在会话已有授权的仓库、操作和范围内执行；用户明确要求提交即构成范围内授权，不重复请示。未授权不改索引、引用、历史或远端。委派按主审分配的权限执行。
6. 保留与本次范围无关的修改、配置、文件头和历史资料。当前架构/调用说明仅在授权范围内同步，历史快照保留其版本身份。

### 暂存区与工作区

用户说「整理我暂存的代码」时，读取 `git diff --cached --name-only`、`git diff --cached -- <path>` 和 `git show :<path>`，再读 `git diff -- <path>` 区分未暂存修改。注释要符合所选版本，不能把暂存版合同贴到行为不同的工作区代码上。重叠处无法安全落地时，提供该版本可审阅的注释片段和准确位置，完成其余范围；读取暂存内容本身不授权写索引。

## 3. 注释先写事实，再写原因

### 函数合同

- 本次触碰的公开函数、任务、IRQ 入口、复杂或有安全副作用的函数保留一份清楚的接口说明，形式按项目规范。采用 Jovi 样式时使用 `Name/Input/Output/Description` 函数头。简单私有 helper 可省略；会改状态、发命令、决定恢复或时序资格的短函数仍需写清合同。
- 注释中展示的签名与实际完整签名一致，保留返回类型、`static` 等限定词及完整参数，禁止用 `(...)` 隐去关键合同。移正贴错位置的头，去掉重复旧头；不为替换风格而改无关文件头或供应商说明。
- 输入说明覆盖本函数怎样使用每个参数、单位、有效范围及必要前提。输出说明覆盖返回值和失败语义；输出参数、状态或硬件副作用写在合同的适当位置。
- 行为说明覆盖真实执行上下文、状态/硬件副作用、阻塞/超时，以及失败后保留、清除或等待什么恢复条件。只描述本函数及其真实调用链，不把调用方的完整流程贴过来。
- 「再次检查」「已关闭」「只读预览」「只用于诊断」都必须能从实际读写及消费者证明。参数传入的是先前结论时，不写成本函数重新读取硬件。

### 定义、使用与粒度

- 字段、宏、枚举、参数，以及承担单位、门槛或状态的局部量，在定义或接口合同处说明含义、单位、生产者/允许写入者和必要失效条件。别在每次赋值处重新定义同一事实。
- 注释解释关键判断的依据及后果：资格如何变化、走向哪里、保留还是撤销哪些状态。按需要覆盖提前返回、`switch/case`、循环结束、限幅、调用、提交与恢复。
- 一处事实只解释一次。函数头说明调用合同，行内说明本处原因和后果；独立的写前/写后复核、样本期限、事件代次或硬件时序各有不同目的时不能当作重复删掉。
- 普通注释任务不要求每行代码、每个显然赋值或每个空函数都有说明。初始化代码可按实际配置阶段分节，再说明关键动作。用户明确要求逐行时，按其粒度覆盖条件、调用、转换、写入和返回，仍解释本行用途，避免照抄标识符。
- 故意空着的分支写清不改变什么及原因；空循环若实际无限等待，不能仅写「等待稳定」掩盖没有超时的事实。
- 使用中文短句。专业缩写可保留，但首次需要用白话讲清行为；不要把「Arm」「夹窝」「功率帽」「pending」单独当解释。

### 数据与上下文

- 查清可变上下文的初始化/重置入口、有效生命周期、真实调用域、唯一或多个写者、跨阶段保留字段；保存外部指针时说明对象寿命。只有代码和调度确有共享时才写锁/临界区要求，不能凭对象名称猜并发。
- 多个 `bool` 分别说明 true/false 的含义、来源时点及消费决策，区分事实、资格、命令、事件和否决。不得把不同资格压成「标志位」。
- 时间、次数和新样本分开说明。收到节拍、实际执行任务、取得新采样、真正积分是不同事件；说明回绕、长间隔和缺样时实际采用的规则。
- 对转换、乘法和累计核对参与类型、范围、单位及饱和/回绕；乘法后才强转不能注释成已防中间溢出。
- 解释零值时先查模式和消费者：可能是合法零、未启用、无效或停机请求。缓存写出实际键、更新与失效条件；预览先查间接写入；诊断/对照字段先查真实生产消费者。

## 4. 硬件、保护和调度按本工程核实

| 核实对象 | 注释边界 |
|---|---|
| 输出状态 | 区分计算结果、资格、已提交命令、驱动设定和物理生效；以实际链路为准，不因这些语义就要求新增同名模块或字段 |
| 执行器反馈 | 区分软件记录、命令寄存器、传感器反馈和物理动作；没有对应反馈不能写成已经测得实际状态 |
| 波形与传能 | 比较值、极性、预装载、更新事件和关断值按器件/当前配置解释；不能从单个寄存器值或模式名承诺全部工况的物理表现 |
| 保护与恢复 | 写实际触发、锁止、清除、恢复资格及执行者；名称和函数拆合方式由本项目决定 |
| 时间调度 | 写实际 ISR、主循环或 RTOS 任务上下文和服务方式；周期与优先级来自本项目合同，不能把节拍通知写成精确周期执行 |
| IRQ/回调 | 查调用链与预算；有界搬运、组帧、事件、快照及紧急关断可发生在 ISR，不能一律注释成只置标志或禁止组帧 |
| 正常与紧急输出 | 若正常动作集中在前台输出入口，注明其范围；硬件/驱动 ISR 的紧急关断无需等待前台，不把「唯一正常写点」写成禁止紧急关断 |
| 存储与通信 | 区分 RAM 待保存、写入成功、校验/提交完成、ACK 入队、发送完成和对端收到；分别说明失败与恢复 |
| 真实消费者 | 控制、恢复、协议、运维/遥测和 Host 各按用途说明，不能仅凭名称判断有无生产用途 |

参考工程、技能示例和历史报告只能提供待核实的线索。发现当前实现与批准合同矛盾时列清冲突；不要用注释把它伪装成符合合同，也不在纯注释任务中重构状态机。没有采用某个例子的名称或结构，本身不构成不合格。

协议/芯片资料优先采用本工程对应版本。记录确实查到的路径、章节或出处；资料缺失时注明未知，不能编造枚举含义、单位或引用。寄存器清标志、屏障、DMA 可见性、RS-485 回声及 RTOS ISR API 均按目标器件和驱动合同核实。

## 5. 只为真实缺口写 todo

仅对本次相关、尚未验证或待确定且确需后续动作的事项，在最贴近代码的位置使用：

```c
// todo: [待验证对象]；验证动作：[怎么验证]；通过标准：[可观察的判据或已批准合同]
```

- 使用小写 `// todo:`、ASCII 冒号和冒号后单空格；不重复堆同一疑点，不用「后面看看」「待上板」代替标准。
- 静态能证明的范围、已核实的资料事实，以及仅与参考工程写法不同的地方，不自动新增 todo。没有本版板测也不意味着每行硬件代码都需要一个 todo。
- 先核对旧 todo 对应的代码、版本和证据；已完成的可移除行级待办并在项目权威记录中注明证据，失效的按当前事实改写。不能照抄历史待办为当前 BUG，也不能只凭旧日志关闭当前验证项。
- 函数头确有「待确认」时落实为具体可追踪事项；代码局部问题在相应行附近标记，整体验收缺口集中记录并关联该入口，不机械给每个调用点加标记。
- 尚无验收阈值时明确缺哪个产品/硬件合同，不能凭参考工程编造数值。缺口影响当前安全或行为取舍时提出具体问题；其余已授权工作继续。

## 6. 格式和布局的等价门

先采用项目现行样式。采用本技能 Jovi 格式时，`.c` 分节用短 `/* 标题 */`，`.h` 分节用 `//=================== 标题 ===`；头文件函数声明单行配行尾中文，标题下一行即代码，分节间一行空行。具体模板见资源表。

纯注释不补大括号、不移动声明、不重排成员、不改字符串日志，也不覆盖 `.clang-format` 或 VS Code 设置。用户授权对应格式/布局动作后：

1. 大括号调整逐个核对控制体、`else` 绑定、宏展开、预处理边界及作用域，不能仅凭视觉认为等价。
2. 文件级 `static` 变量/原型可按项目习惯集中到函数前，但仅在原作用域、原条件守护及类型/宏/初始化依赖不变时前置；不移动函数内 `static`，不跨 `#if`，不为布局拆合条件块。
3. 仅在本次要求或项目规范采用同声明类型分组时检查该样式；语义分组等其他已采用布局不因此构成问题。固定 Flash/协议/DMA/寄存器/packed/bitfield/ABI 布局按实际约束保留。成员重排交已授权的结构修改范围，不扩展到形参、不新增嵌套结构或公共头、不凭宽度宣称节省固定 RAM。
4. 配置同步仅在授权范围，合并已有设置；内置 clang-format 控制样式，不会自动补大括号。只保留配置或处理单文件，不能声称全范围已经统一。
5. 格式转换还要考虑 `__LINE__`、多行宏、反斜杠换行及预处理意义，`//` 不能吞掉原代码或宏的后续行。

## 7. 执行与完成检查

1. **建立清单**：记录选定版本、文件/函数、用户粒度、允许的注释/格式/布局和已有逻辑差异；读取第 2 节相关资源。
2. **查真实合同**：从定义、调用、状态读写、消费者、资料与批准需求核对上下文、单位、前提、失败及恢复。发现命名不符、重复判断、缓存缺键或错误宏可见性时给出可达路径，交 `code_sc/code_wrt`，不靠文字掩盖。
3. **局部编辑**：保留有用内容，补必要合同与行内原因，移正错位函数头，合并重复说明；模板只应用于本次授权范围。
4. **逐文件复核**：按 diff 检查完整签名、字段/分支粒度、数字单位、软硬件边界、todo 与实际修改相符。用 `rg` 检索旧名/术语时区分活动源码、当前文档、历史快照和 SDK/协议/ABI 名，不恢复已删除兼容别名来遮掩残留。
5. **核对等价**：纯注释比较本次前后 C token、预处理和宏续行；授权格式/布局另查控制体、守护、可见性和依赖。需要时使用已有语法/构建检查；不为低风险文字改动增加无关测试，也不以 grep 或脚本退出 0 代替语义检查。
6. **分层报告验证**：当前源码静态检查、Host、目标编译链接和实板分别写通过/失败/未执行/受阻，并注明版本与证据。旧 Host、旧 map 或上一轮板测不能写成本版通过；编译通过不证明物理响应、闭环稳定或机械触点状态。
7. **交付收口**：报告本批目标、具体文件与变化、实际验证、未决问题和下一步。同步已约定的当前文档/任务入口；固件版本按项目策略和用户范围处理，不因纯注释自动升固件版本。已有 Git 授权按范围完成，无授权只交付工作区变化。

多文件可按不重叠文件分配子 Agent，注明版本、粒度、允许动作和证据要求；主审统一查交界、重复事实和 Git 状态。不要为小任务机械增加角色或文件。
